## 1. 프로젝트 정체성

LearnCosmos는 기존 LearnWeaver의 기획, 구현, 문서 자산을 기반으로 다시 시작하는 AI 기반 자기주도 학습 플랫폼이다.

핵심 방향은 다음 한 문장으로 확정한다.

> 콘텐츠를 학습 경험으로 바꾼다.

LearnCosmos는 단순 콘텐츠 추천 서비스나 AI 코스 생성 서비스가 아니다. 사용자가 본 영상, 읽은 글, 들은 수업, AI에게 받은 답변을 목표, 스킬, 반복 기록, 질문, 복습, 결과물로 연결해 실제 학습 경험으로 소화하도록 돕는 서비스다.

---

## 2. 핵심 제품 원칙

1. 정답 제공보다 학습자가 스스로 관찰하고 기록하게 한다.
2. 콘텐츠 소비보다 학습 소화와 자기 언어화를 강화한다.
3. 학습 목표, 필요한 스킬, 반복 기록, 질문, 복습, 결과물을 연결한다.
4. 사용자가 기록하고 싶은 학습 경험을 만든다.
5. 모바일 중심 UX에서 부담 없이 작동해야 한다.
6. Lumi는 명령자가 아니라 친절한 안내자여야 한다.
7. 구현 복잡도와 운영 리스크를 과도하게 키우지 않는다.
8. 베타 단계에서는 검증 가능한 작은 단위로 나누어 구현한다.

## 3.1 브랜드 전환과 로고 의미

### LearnWeaver에서 LearnCosmos로

LearnWeaver는 사라지는 이름이 아니라 LearnCosmos가 시작된 출발점이다.

처음 LearnWeaver라는 이름에는 배움의 조각들을 엮는다는 의미가 담겨 있었다. 학습 목표를 정리하고, 콘텐츠를 연결하고, 학습 경로를 만들고, 기록을 쌓아 가는 구조에서는 Weaver라는 이름이 잘 맞았다. 지식과 경험을 엮어 가는 서비스라는 뜻이 분명했기 때문이다.

하지만 서비스가 발전하면서 단순히 배움의 조각을 엮는 것을 넘어, 사용자가 자기만의 학습 세계를 만들고 그 세계를 탐험하며 완성해 가는 방향이 더 중요해졌다. 그래서 사용자에게 보일 브랜드명은 LearnCosmos로 전환한다.

LearnCosmos는 배움을 하나의 우주로 바라보는 이름이다. 사용자가 배우고 싶은 주제는 하나의 행성이 되고, 그 행성 안에는 여러 지역이 생기며, 각 지역에는 탐험 지점이 놓인다. 학습자는 그 지점을 따라가며 콘텐츠를 보고, 직접 시도하고, 막힌 부분을 기록하고, 해결한 과정을 남긴다.

그렇게 하나의 배움은 단순한 강의 목록이 아니라 사용자가 직접 탐험하고 완성해 가는 세계가 된다.

Cosmos는 단순히 우주라는 뜻만이 아니라, 흩어진 것들이 질서를 이루는 세계라는 의미도 함께 담고 있다. LearnCosmos가 만들고 싶은 학습도 그렇다. 흩어진 콘텐츠, 질문, 기록, 결과물이 하나의 목표를 중심으로 연결되고, 학습자만의 배움 세계로 정리되는 구조다.

### 로고 의미

LearnCosmos 로고는 파란 행성, 보라색 궤도, 노란 별을 중심 상징으로 사용한다.

| 요소 | 의미 |
|---|---|
| 파란 행성 | 사용자가 만들어 가는 자기만의 학습 세계 |
| 보라색 궤도 | 목표를 향해 이어지는 학습 여정 |
| 노란 별 | 성취와 성장의 순간 |

파란 행성은 사용자가 만들어 가는 자기만의 학습 세계를 의미한다. LearnCosmos에서 하나의 코스는 단순히 순서대로 보는 자료 묶음이 아니다. 목표가 있고, 경로가 있고, 탐험 지점이 있으며, 그 안에 기록과 결과물이 쌓이는 하나의 세계다.

행성을 감싸는 보라색 궤도는 목표를 향해 이어지는 학습 여정을 의미한다. 배움은 한 번에 끝나지 않는다. 찾아보고, 시도하고, 막히고, 다시 이해하고, 기록하는 과정이 반복된다. 이 반복되는 흐름을 하나의 궤도로 표현한다.

노란 별은 성취와 성장의 순간을 상징한다. 큰 결과물만 성취는 아니다. 오늘 하나를 이해한 순간, 어려웠던 개념을 넘은 순간, 내 손으로 작은 결과물을 만든 순간도 분명한 성장이다. LearnCosmos는 그런 작은 성취가 학습자의 여정 안에 남기를 지향한다.

### 브랜드 전환 기준

LearnWeaver가 개발 과정의 이름이었다면, LearnCosmos는 앞으로 사용자에게 보여주고 싶은 브랜드 이름이다.

LearnWeaver의 핵심이 배움의 조각을 엮는 것이었다면, LearnCosmos의 핵심은 그 조각들이 모여 하나의 세계가 되고, 여러 세계가 연결되어 학습자의 우주가 되는 것이다.

따라서 신규 문서, 사용자 안내, 서비스 화면, 블로그, 공지, 이미지 제작 기준은 LearnCosmos로 통일한다. 단, 기존 코드, 레거시 문서, 이전 변경 이력에서 LearnWeaver 명칭은 출발점과 계승 자산으로 보존한다.

## 4. 세계관 용어 체계

| 일반 개념 | LearnCosmos 용어 | 확정 의미 |
|---|---|---|
| Course | 행성 | 사용자가 만들고 탐험하는 하나의 학습 세계 |
| Lesson | 지역 | 행성 안에서 탐험하는 학습 구역 |
| SubLesson | 서브지역 | 지역 안의 세부 학습 구역 |
| Point | 지점 | 실제 학습 행동이 일어나는 단위 |
| Exploration Point | 탐험지점 | 외부 또는 플랫폼 학습 콘텐츠를 연결하는 지점 |
| Research Point | 연구지점 | 학습자가 직접 학습 대상을 입력하는 지점 |
| Content | 탐험목표 / 학습 대상 자료 | 사용자가 학습할 콘텐츠 또는 자료 |
| Dashboard | Galaxy / Star System | 학습 행성을 탐색하는 우주 지도 |
| Explorer Diary | 탐험계획 + 탐험일지 | 학습 계획과 학습 기록을 연결하는 핵심 공간 |
| Lumi | 탐험 파트너 | 다음 행동을 친절하게 안내하는 캐릭터 |

탐험지점과 연구지점은 상하 관계가 아니다. 두 지점은 같은 레벨의 학습 지점이며, 차이는 학습 대상이 외부·플랫폼 자료인지 사용자가 직접 입력한 대상인지에 있다.

## 5. 핵심 사용자 흐름

```text
배우고 싶은 주제 입력
→ AI가 행성탐험계획 초안 생성
→ 지역별 탐험목표 구성
→ 지점별 학습 진행
→ 목표 / 스킬 / 반복 / 질문 / 복습 / 결과물 기록
→ 탐험일지 누적
→ 행성탐험완료
```

중요한 것은 코스 생성 자체가 아니라, 생성된 계획이 학습자의 기록과 결과물로 이어지는 것이다.

## 6. Galaxy Dashboard 기준

Galaxy Dashboard는 LearnCosmos의 핵심 진입 화면으로 확정한다.

Galaxy Dashboard는 복잡한 우주 시각화 화면이 아니라, 사용자가 자신의 학습 행성을 빠르게 만들고, 찾고, 상태를 확인하고, 바로 학습으로 진입하는 보드형 화면이다.

### 6.1 핵심 역할

1. LearnCosmos의 핵심 진입 화면
2. 사용자의 행성 목록 확인
3. 탐험 상태 관리
4. Lumi의 상태 안내 제공
5. 행성 생성 진입점 제공
6. 행성 검색 기능 제공
7. 행성 리스트 제공
8. Galaxy Board에서 바로 Explorer Diary 화면으로 진입

### 6.2 제거 기준

Star System 개념은 Galaxy Dashboard 기준에서 제거한다.

기존의 항성계, 중심 태양, 궤도 기반 탐색 개념은 초기 제품 기준에서 제외한다. Galaxy Dashboard는 시각적 세계관을 유지하되, 실제 기능은 행성 생성, 검색, 리스트, 상태 관리, Explorer Diary 진입에 집중한다.

### 6.3 확정 구조

| 영역 | 기준 |
|---|---|
| 행성 생성 | 사용자가 새 학습 주제를 입력하고 행성탐험계획을 생성하는 영역 |
| 행성 검색 | 기존 행성을 제목, 주제, 상태 기준으로 찾는 영역 |
| 행성 리스트 | 사용자의 행성 목록을 카드 또는 리스트 형태로 보여주는 영역 |
| 탐험 상태 | 초안, 진행 중, 완료 등 학습 상태를 확인하고 관리하는 영역 |
| Lumi 안내 | 현재 상태와 다음 행동을 짧고 친절하게 안내하는 영역 |
| Explorer Diary 진입 | 선택한 행성에서 바로 학습계획과 탐험일지 화면으로 이동하는 진입점 |

### 6.4 화면 원칙

1. Galaxy Dashboard는 사용자의 첫 학습 조작 화면이다.
2. 행성 생성, 검색, 리스트가 화면의 중심 기능이다.
3. 행성 카드는 Explorer Diary로 진입하는 직접 경로를 제공한다.
4. 탐험 상태는 사용자가 어느 행성을 계속할지 판단하도록 도와야 한다.
5. Lumi는 현재 행성 상태와 다음 행동을 안내하되, 화면을 방해하지 않는다.
6. 모바일에서는 복잡한 시각 효과보다 검색, 리스트, 이어하기 기능을 우선한다.
7. Star System 기반의 별도 탐색 모드는 초기 기준에서 제외한다.

## 7. Explorer Diary 기준

Explorer Diary는 LearnCosmos의 핵심 학습 공간으로 확정한다.

Explorer Diary는 단순한 코스 편집 화면이 아니다. 사용자가 학습을 계획하고, 실제 학습 중 막힘과 해결, 질문, 복습, 결과물을 기록하는 중심 공간이다.

Explorer Diary의 역할은 다음과 같다.

1. 행성탐험계획 확인 및 수정
2. 지역 / 지점 / 탐험목표 확인
3. 학습 목표 발견
4. 필요한 스킬 정리
5. 반복 학습 기록
6. 막힘과 해결 기록
7. 질문과 복습 기록
8. 결과물 저장
9. 행성탐험완료 판단의 근거 저장

Explorer Diary는 LearnCosmos의 제품 차별점이다. 따라서 초기 MVP에서도 최소한의 기록 구조는 반드시 포함해야 한다.

## 7.3 지점 학습흐름 v2 기준

지점 학습흐름은 LearnCosmos의 핵심 학습 소화 구조로 확정한다. 지점은 콘텐츠를 단순히 소비하는 곳이 아니라, 관찰한 자료를 목표와 스킬로 바꾸고, 반복과 기록을 통해 결과물로 정리하는 학습 단위다.

Point Learning Action Resolver는 이 학습흐름을 새 단계로 대체하지 않는다. Resolver는 지점에 연결된 콘텐츠나 연구자료의 성격을 판단하여, 각 단계의 안내문, 질문, 기록 방식, 결과물 기준, 완료 조건을 현재 학습흐름에 맞게 바꾸는 내부 판단 레이어다.

### 7.3.1 지점 학습흐름 v2

```text
1. 지점 관찰
   - 영상 시청 또는 학습자료 분석
   - Resolver가 자료 성격 판단
   - 이 자료로 무엇을 해볼지 학습방법 추천
   - 목표 찾기
   - 필요한 스킬 찾기

2. 스킬 반복
   - 선택한 스킬별 반복 수행
   - 자료 성격에 맞는 반복 방식 적용
   - 질문하고 해답찾기
   - 자기평가 기록
     · 무엇을 모르는가
     · 무엇이 안 되는가
     · 무엇을 이해했는가
     · 무엇이 발전했는가

3. 결과 정리
   - 모든 스킬을 완료한 결과물 기록
   - 배운 내용을 자기 언어로 정리
   - 자료 유형에 맞는 증거 남기기
     · 요약문
     · 체크리스트
     · 코드
     · 녹음/녹화
     · 작품
     · 문제풀이
     · 수정 로그

4. 완료 확인
   - 결과물에 대한 자기평가
   - 목표 달성 여부 확인
   - 반복 기록 확인
   - 질문하고 해답찾기 기록 확인
   - 다음 보완점 기록
   - 지점 완료 판단
```

### 7.3.2 기존 6단계 PRD와 현재 4단계 흐름의 관계

기존 Point Learning Action Resolver PRD의 6단계는 다음과 같다.

```text
지점 관찰
→ 목표물 발견
→ 필요한 기술 발견
→ 반복 탐험
→ 최종 발견물
→ 지점 완료
```

이 6단계는 폐기하지 않고 현재 지점 학습흐름 v2의 4단계 안으로 흡수한다.

| 기존 PRD 표현 | 현재 학습흐름 v2 반영 |
|---|---|
| 지점 관찰 | 지점 관찰 |
| 목표물 발견 | 지점 관찰 안의 목표 찾기 |
| 필요한 기술 발견 | 지점 관찰 안의 스킬 찾기 |
| 반복 탐험 | 스킬 반복 |
| 최종 발견물 | 결과 정리 |
| 지점 완료 | 완료 확인 |

### 7.3.3 Point Learning Action Resolver 정의

```text
Point Learning Action Resolver
= 지점에 연결된 콘텐츠나 연구자료를
  지점 학습흐름 v2에 맞는 구체적 학습 행동으로 바꾸는 내부 판단 레이어
```

Resolver의 역할은 다음과 같다.

1. 사용자는 항상 지점 학습흐름 안에서 학습한다.
2. Resolver는 새 화면 단계를 추가하지 않는다.
3. Resolver는 각 단계의 질문, 안내문, 기록 방식, 결과물 조건을 바꾼다.
4. 콘텐츠 형식만으로 학습방법을 정하지 않는다.
5. `point_type`, `content_format`, `content_role`, `goal_type`을 함께 판단한다.
6. 영상 시청 자체는 완료 조건이 아니다.
7. 완료는 목표, 스킬, 반복 기록, 결과물, 자기평가로 판단한다.

### 7.3.4 Resolver 판단 기준

Resolver는 다음 요소를 함께 본다.

| 판단 요소 | 의미 |
|---|---|
| point_type | 탐험지점인지 연구지점인지 |
| content_format | 영상, 글, 이미지, 코드, 파일, 직접 입력 자료 등 자료 형식 |
| content_role | 개념 설명, 튜토리얼, 문제풀이, 사례, 오류 진단, 질문 등 자료 역할 |
| goal_type | 이해, 적용, 제작, 수행, 진단, 탐구 등 학습 목표 성격 |

핵심 원칙은 콘텐츠 형식만으로 학습방법을 결정하지 않는 것이다. 예를 들어 YouTube 영상이라도 개념 설명 영상인지, 튜토리얼인지, 문제풀이 영상인지, 사례 분석 영상인지에 따라 학습 행동은 달라진다.

### 7.3.5 method_type 사전

자료 성격에 따라 Resolver는 다음 학습방법 후보를 추천한다.

| method_type | 쓰이는 경우 | 핵심 학습행동 |
|---|---|---|
| understand_extract | 개념 영상, 블로그, 문서 | 핵심 개념 추출, 자기 말로 설명 |
| watch_practice | 영상 튜토리얼 | 멈춰가며 따라 하기 |
| solve_compare | 문제풀이 영상, 문제 자료 | 먼저 풀고 해설과 비교 |
| read_apply | 절차형 블로그, 가이드 | 절차를 체크리스트로 바꿔 실행 |
| make_iterate | 프로젝트 제작, 창작, 코딩 | 결과물 v1 제작 후 개선 |
| perform_record | 운동, 악기, 말하기, 발음 | 수행 후 녹음/녹화/횟수 기록 |
| compare_diagnose | 연구지점 사진, 영상, 작품 | 현재 결과를 기준과 비교 진단 |
| debug_improve | 사용자 코드, 에러 | 수정-실행-기록 반복 |
| case_apply | 사례 분석, 리뷰 글, 영상 | 사례에서 원칙 추출 후 내 상황에 적용 |
| question_to_inquiry | 사용자 질문, 궁금증 | 질문을 탐구 과제로 바꿈 |

### 7.3.6 단계별 Resolver 작동 방식

#### 1단계. 지점 관찰

Resolver는 자료 성격에 맞는 관찰 질문을 제시한다.

예:

```text
이 자료를 보고 무엇을 할 수 있어야 할까요?
이 자료에서 가장 중요한 내용은 무엇인가요?
그 목표를 위해 필요한 스킬은 무엇일까요?
```

#### 2단계. 스킬 반복

Resolver는 method_type에 따라 반복 방식을 제안한다.

예:

```text
무엇을 반복했나요?
어디서 막혔나요?
어떤 질문이 생겼나요?
어떤 해답을 찾았나요?
무엇을 이해했나요?
무엇이 발전했나요?
```

#### 3단계. 결과 정리

Resolver는 자료 성격에 따라 결과물 기준을 다르게 제시한다.

| 자료 성격 | 결과물 예시 |
|---|---|
| 개념 자료 | 자기 언어 요약, 개념 설명문 |
| 튜토리얼 | 따라 만든 결과물, 캡처, 링크 |
| 문제풀이 | 풀이 과정, 오답 정리 |
| 절차형 가이드 | 실행 체크리스트, 적용 결과 |
| 창작/코딩 | 결과물 v1, 개선 버전 |
| 말하기/운동/악기 | 녹음, 녹화, 횟수 기록 |
| 코드/에러 | 수정 로그, 실행 결과 |
| 질문/탐구 | 탐구 결론, 참고자료, 내 답변 |

#### 4단계. 완료 확인

완료 확인은 콘텐츠 소비량이 아니라 학습 결과를 기준으로 판단한다.

완료 조건은 다음과 같다.

```text
- 목표를 찾았는가
- 필요한 스킬을 정리했는가
- 스킬 반복 기록이 있는가
- 질문하고 해답찾기 기록이 있는가
- 결과물이 남았는가
- 결과물에 대한 자기평가가 있는가
```

### 7.3.7 YouTube 및 외부자료 완료 기준

YouTube 영상이나 외부자료는 LearnCosmos가 소유하거나 판매하는 콘텐츠가 아니다. LearnCosmos는 외부 자료를 목표, 스킬, 반복, 기록, 결과물, 자기평가로 바꾸는 학습 도구를 제공한다.

정책 문구는 다음과 같이 정리한다.

```text
영상은 YouTube에서 재생됩니다.
LearnCosmos는 영상 시청권이 아니라,
이 자료를 목표·스킬·반복·기록·결과물·자기평가로 바꾸는 학습 도구를 제공합니다.
```

완료 조건이 아닌 것은 다음과 같다.

```text
- 영상 재생
- 영상 시청 시간
- YouTube 좋아요
- YouTube 구독
- YouTube 댓글
```

완료 조건이 되는 것은 다음과 같다.

```text
- 목표 찾기
- 스킬 선택 또는 정리
- 반복 기록
- 질문하고 해답찾기 기록
- 결과물 또는 증거
- 자기평가
```

### 7.3.8 교육학적 의미

이 흐름은 자기조절학습, 수행중심학습, 메타인지, 포트폴리오 학습을 LearnCosmos 방식으로 결합한 구조다.

| 학습흐름 | 교육학적 의미 |
|---|---|
| 지점 관찰 | 과제 이해, 학습 대상 탐색, 목표 설정 |
| 목표 찾기 | 학습 목표 구체화, 성공 기준 파악 |
| 스킬 찾기 | 필요한 하위 능력 분해 |
| 스킬 반복 | 의도적 연습, 숙달 학습, 수행 기반 학습 |
| 질문하고 해답찾기 | 탐구학습, 문제해결학습, 메타인지 활성화 |
| 자기평가 | 자기조절학습, 성찰, 피드백 루프 |
| 결과 정리 | 산출물 기반 학습, 수행평가, 포트폴리오 |
| 완료 확인 | 성취 기준 확인, 다음 학습 조정 |

최종적으로 지점 학습흐름은 다음 구조로 정리한다.

```text
지점 관찰
→ 목표 찾기
→ 스킬 찾기
→ 스킬 반복
→ 질문하고 해답찾기
→ 자기평가
→ 결과 정리
→ 완료 확인
```

이 구조가 LearnCosmos의 핵심 문장인 “콘텐츠를 학습 경험으로 바꾼다”를 실제 화면에서 작동하게 만드는 기준이다.

## 8. Lumi 역할 기준

Lumi는 LearnCosmos의 탐험 파트너로 확정한다.

역할은 다음과 같다.

1. 사용자의 현재 상태를 설명한다.
2. 다음 행동을 친절하게 안내한다.
3. Dashboard에서 hover / selection 상태를 해석해 짧게 안내한다.
4. Explorer Diary에서 기록을 돕는다.
5. 학습자를 압박하거나 명령하지 않는다.

금지 기준은 다음과 같다.

1. Lumi를 독립 튜터처럼 과도하게 판단시키지 않는다.
2. 사용자의 학습을 대신 끝내는 구조로 만들지 않는다.
3. 정답 제공 중심 챗봇으로 만들지 않는다.
4. 모바일에서 과도한 애니메이션이나 공간 점유를 만들지 않는다.

## 9. AI 기능 기준

LearnCosmos의 AI는 학습을 대신하는 기능이 아니라 학습자가 학습을 구조화하도록 돕는 도구다.

확정 AI 기능은 다음과 같다.

| 기능 | 확정 방향 |
|---|---|
| 행성탐험계획 생성 | 주제 입력을 기반으로 초안 생성 |
| 지역 구성 | 목표에 맞는 학습 단위 생성 |
| 콘텐츠 추천 | 내부 자료 우선, 부족 시 외부 후보 보강 |
| 학습 기록 보조 | 사용자의 막힘, 해결, 질문, 복습을 정리하도록 도움 |
| 결과물 정리 보조 | 학습자의 산출물을 자기 언어로 정리하도록 도움 |

AI 사용 원칙은 다음과 같다.

1. AI는 정답 제공자가 아니라 학습 구조화 도구다.
2. 사용자가 직접 기록하고 판단하는 여지를 남긴다.
3. 외부 자료 추천은 검증과 중복 제거가 필요하다.
4. 잘못된 추천이 반복되지 않도록 차단 / 보류 / 검수 구조를 둔다.

## 10. 콘텐츠 추천 기준

콘텐츠 추천은 LearnCosmos의 보조 기능이다. 핵심은 추천 자체가 아니라 추천된 자료를 학습 경험으로 전환하는 것이다.

확정 원칙은 다음과 같다.

1. 내부 자료를 우선 사용한다.
2. 내부 자료가 부족할 때 외부 검색을 보강한다.
3. 외부 검색 결과는 추천 시점에 무조건 내부 저장하지 않는다.
4. 학습자가 선택한 외부 자료만 저장 대상으로 삼는다.
5. URL / canonical URL / external id 기준으로 중복을 제거한다.
6. 깨진 링크, 제한 콘텐츠, 품질 낮은 자료는 추천에서 제외한다.
7. 추천 결과에 대한 운영 점검 구조를 유지한다.

BYOK와 AI 포인트 구조는 유지하되, 사용자에게는 어렵지 않게 안내한다.

| 항목 | 기준 |
|---|---|
| 시스템 키 | 기본 AI 사용 경로 |

| 포인트 | 시스템 키 사용 시 과금 기준으로 사용 |
| 일반 사용자 UX | AI 포인트 중심으로 안내 |
| 고급 사용자 UX | 내 API 키 연결 방식으로 분리 안내 |

## 12. 문서 체계 기준

LearnCosmos의 문서 기준 구조는 다음과 같이 확정한다.

```text
LearnCosmos/
└─ docs/
   ├─ master/
   ├─ wiki/
   ├─ plans/
   ├─ decisions/
   ├─ sessions/
   └─ versions/
```

문서별 역할은 다음과 같다.

| 위치 | 역할 |
|---|---|
| docs/master | 현재 기준 단일 원본 |
| docs/wiki | 반복 참고용 지식 허브 |
| docs/plans | 구현 전 계획과 분석 |
| docs/decisions | 되돌리기 어려운 결정 기록 |
| docs/sessions | 논의 맥락과 작업 기록 |
| docs/versions | 과거 기준 스냅샷 |

Wiki는 Master를 대체하지 않는다. Wiki는 기준 원본으로 빠르게 이동하기 위한 탐색 / 요약 / 연결 레이어다.

## 13. MVP 확정 방향

1차 MVP는 다음 범위로 제한한다.

1. 주제 입력
2. 행성탐험계획 생성
3. Dashboard / Galaxy 진입
4. Explorer Diary 기본 화면
5. 지역 / 지점 / 탐험목표 구조 확인
6. 최소 학습 기록
7. Lumi 기본 안내

후순위는 다음과 같다.

1. 크리에이터 기능
2. 커뮤니티 기능
3. 그룹 코스
4. 고급 공유 기능
5. 고급 분석 리포트
6. Lumi 고도화 대화 기능

초기 MVP는 AI 코스 생성 서비스가 아니라 학습계획과 학습기록을 연결하는 서비스로 출시한다.

## 13.1 커뮤니티 기획 기준

커뮤니티는 LearnCosmos의 1차 MVP 핵심 기능은 아니지만, 개인학습 흐름과 연결되는 P2 확장 기획으로 보존한다.

커뮤니티의 최신 기준은 LearnCosmos 개인학습 중심 IA/UX 재설계 문서 세트 v2의 `06_community_menu.md`를 따른다.

### 13.1.1 커뮤니티 정의

```text
커뮤니티
= 개인학습에서 생긴 질문, 기록, 결과물, 루틴을
  다른 학습자와 연결하는 학습 상호작용 공간
```

LearnCosmos의 커뮤니티는 일반 게시판이 아니다. 지점 학습흐름과 Explorer Diary에서 생긴 질문, 결과물, 반복 기록, 자기평가가 다른 학습자와 연결되는 공간이다.

따라서 커뮤니티는 콘텐츠 소비 이후의 잡담 공간이 아니라, 개인학습을 확장하는 학습 상호작용 레이어로 정의한다.

### 13.1.2 커뮤니티 메뉴 구조

```text
커뮤니티
├─ 커뮤니티 홈
├─ 커뮤니티 찾기
├─ 내 커뮤니티
└─ 만들기
```

| 메뉴 | 역할 |
|---|---|
| 커뮤니티 홈 | 추천 커뮤니티, 인기 커뮤니티, 내 커뮤니티 요약을 보여주는 입구 |
| 커뮤니티 찾기 | 활동 승인된 커뮤니티를 검색하고 참여하는 화면 |
| 내 커뮤니티 | 내가 만든, 운영 중인, 참여 중인, 요청 중인 커뮤니티를 관리하는 화면 |
| 만들기 | 커뮤니티 생성, 운영 규칙 설정, 초기 멤버 초대, 활동 승인 준비 화면 |

### 13.1.3 커뮤니티 생성/승인 구조

커뮤니티는 아무나 만들고 바로 공개 활동하는 구조가 아니다. 생성자와 초기 멤버 조건을 충족해야 본격 활동이 가능하다.

```text
커뮤니티 만들기
→ 기본 정보 입력
→ 운영 규칙 설정
→ 초기 멤버 초대
→ 최소 멤버 수 충족
→ 활동 허가
→ 공개/운영 시작
```

### 13.1.4 커뮤니티 상태 모델

```text
draft
→ recruiting
→ ready
→ active
→ paused
→ archived
```

| 상태 | 의미 |
|---|---|
| draft | 생성자가 기본 정보를 작성 중 |
| recruiting | 초기 멤버를 모으는 중 |
| ready | 최소 조건 충족, 시작 전 |
| active | 본격 활동 허가 상태 |
| paused | 운영 중지 또는 검토 상태 |
| archived | 종료 또는 보관 상태 |

사용자 노출 상태는 다음과 같이 단순화한다.

```text
준비중
→ 멤버 모집중
→ 활동 가능
→ 활동중
→ 종료
```

### 13.1.5 활동 승인 조건

초기 기준은 생성자 포함 3명 이상으로 한다. 정식 오픈 이후에는 생성자 포함 5명 이상으로 확장할 수 있다.

최소 조건은 다음과 같다.

```text
- 커뮤니티 이름 있음
- 소개 문구 있음
- 학습 주제 선택됨
- 운영 규칙 있음
- 생성자 있음
- 생성자 포함 3명 이상
- 안전 정책 동의
```

조건 충족 시 상태는 다음처럼 전환한다.

```text
recruiting → active
```

### 13.1.6 공개 범위

커뮤니티 공개 범위는 초기 기준에서 다음 3가지로 정리한다.

| 유형 | 검색 노출 | 참여 방식 |
|---|---|---|
| 공개 | 노출 | 바로 참여 |
| 승인제 | 노출 | 참여 요청 후 승인 |
| 초대 전용 | 기본 검색 제외 또는 제한 노출 | 초대 링크 필요 |

검색 노출은 active 상태의 공개/승인제 커뮤니티만 기본 노출한다. draft, paused, archived 상태는 일반 검색 노출에서 제외한다.

### 13.1.7 커뮤니티 내부 기능

활동 승인 후 사용할 수 있는 커뮤니티 내부 기능은 다음과 같다.

```text
커뮤니티 내부
├─ 홈
├─ 질문
├─ 결과물
├─ 학습 모임
├─ 공지
└─ 멤버
```

커뮤니티 내부 기능은 피드형 SNS보다 질문, 결과물, 학습 모임, 공지, 멤버 관리 중심으로 설계한다.

### 13.1.8 개인학습과 커뮤니티 연결

커뮤니티는 Explorer Diary와 지점 학습흐름에서 파생된다.

```text
탐험일지의 질문
→ 커뮤니티 질문으로 공유
→ 답변 받기
→ 탐험일지에 반영

결과물
→ 커뮤니티 결과물 공유
→ 피드백 받기
→ 개선 기록으로 반영

반복 루틴
→ 학습 모임/모각공 참여
→ 루틴 유지
```

즉, 커뮤니티는 학습을 대신하는 공간이 아니라 개인학습에서 나온 질문, 결과물, 반복 기록을 확장하는 공간이다.

### 13.1.9 Explorer Diary 커뮤니티 활성 기준

이전 확정 결정에 따라 커뮤니티는 공유 이후에만 열리는 페이지가 아니라, 학습 시작과 함께 제한적으로 활성된다.

활성 트리거는 다음과 같다.

```text
ready → learning 전이 시 커뮤니티 기본 연결 시작
탐험일지에서 질문 작성 시 질문/답변 축 생성
탐험일지에서 결과물 업로드 시 결과물 평가/피드백 축 연결
```

상태별 정책은 다음과 같다.

| 상태 | 커뮤니티 정책 |
|---|---|
| learning | 질문 작성, 관련 질문/답변/팁/피드백 검색, 크리에이터 도움 요청 가능 |
| completed + private | 본인 중심 읽기, 내 질문 추가, 내 결과물 피드백 요청, 내 스레드 후속 댓글 가능 |
| completed + shared | 공개 코스 기준 상호작용 완전 활성 |

단, 공개 확산과 커뮤니티 전체 토론은 shared 이후에 본격 활성한다.

### 13.1.10 구현 우선순위

커뮤니티는 P2 확장 기능으로 둔다.

우선 구현 후보는 다음과 같다.

```text
- 커뮤니티 홈
- 커뮤니티 찾기
- 검색 필터
- 커뮤니티 카드
- 참여하기
- 내 커뮤니티
- 커뮤니티 만들기
- 기본 정보 입력
- 운영 규칙 입력
- 초기 멤버 초대
- 활동 승인 조건
```

### 13.1.11 설계 원칙

1. 커뮤니티는 개인학습의 확장 공간이다.
2. 커뮤니티는 생성자와 초기 멤버 조건을 가진다.
3. 활동 승인된 커뮤니티만 기본 검색에 노출한다.
4. 공개, 승인제, 초대 전용 공개 범위를 둔다.
5. 질문과 결과물은 개인학습 기록에서 파생될 수 있어야 한다.
6. 커뮤니티는 루틴 유지와 피드백 교환을 돕는다.
7. 커뮤니티는 1차 MVP가 아니라 P2 확장 기획으로 관리한다.

## 13.2 크리에이터 기획 기준

크리에이터는 LearnCosmos의 1차 MVP 핵심 기능은 아니지만, 개인학습과 지점 학습흐름을 확장하는 P2 확장 기획으로 보존한다.

크리에이터의 최신 기준은 LearnCosmos 개인학습 중심 IA/UX 재설계 문서 세트 v2의 `07_creator_menu.md`를 따른다.

### 13.2.1 크리에이터 정의

```text
크리에이터
= 학습자가 콘텐츠를 보고 목표물과 필요한 스킬을 발견할 수 있도록
  학습 콘텐츠, 목표물 예시, 스킬 후보, 반복 가이드, 결과물 기준을 설계하는 사람
```

LearnCosmos의 크리에이터는 단순 강의 판매자가 아니다. 크리에이터는 학습경험 설계자다.

크리에이터는 학습자가 지점에서 다음 흐름을 잘 수행할 수 있도록 학습 구조를 설계한다.

```text
지점 관찰
→ 목표 찾기
→ 스킬 찾기
→ 스킬 반복
→ 질문하고 해답찾기
→ 결과 정리
→ 완료 확인
```

### 13.2.2 크리에이터 메뉴 구조

초기 기준 메뉴는 다음과 같다.

```text
크리에이터
├─ 크리에이터 소개
├─ 콘텐츠 만들기
├─ 그룹 코스
├─ 내 콘텐츠
└─ 피드백
```

확장 후보는 다음과 같다.

```text
크리에이터
├─ 콘텐츠 분석
├─ 수익화
└─ 정산
```

초기에는 수익화와 정산을 전면에 두지 않는다. 수익화는 학습 가치가 검증된 뒤 단계적으로 적용한다.

### 13.2.3 크리에이터 신청/승인 구조

초기 베타에서는 신청/승인 구조를 둔다.

```text
크리에이터 신청
→ 프로필 입력
→ 전문 분야 선택
→ 샘플 콘텐츠 제출
→ 운영 검토
→ 크리에이터 승인
→ 콘텐츠 등록 가능
```

신청 항목은 다음과 같다.

```text
- 이름/닉네임
- 소개
- 전문 분야
- 만들고 싶은 콘텐츠 유형
- 참고 링크 또는 샘플
- 운영 기준 동의
```

크리에이터 신청/승인 구조는 콘텐츠 품질 관리, 학습 안전성, 서비스 운영 신뢰도를 위해 유지한다.

### 13.2.4 콘텐츠 만들기 구조

크리에이터 콘텐츠는 단순 자료 업로드가 아니다. 학습자가 콘텐츠를 보고 무엇을 만들고, 어떤 스킬을 반복하고, 어떤 결과물을 남겨야 하는지 안내하는 탐험지점 후보로 설계한다.

```text
콘텐츠 만들기
├─ 기본 정보
├─ 학습 콘텐츠
├─ 목표물 예시
├─ 필요한 스킬 후보
├─ 반복 탐험 가이드
├─ 결과물 기준
├─ 자주 막히는 부분
└─ 공개 설정
```

### 13.2.5 기본 정보

```text
- 콘텐츠 제목
- 설명
- 카테고리
- 난이도
- 예상 학습 시간
- 대상 학습자
- 태그
```

### 13.2.6 학습 콘텐츠 기준

베타에서는 외부 링크 기반 콘텐츠를 우선 지원한다.

지원 후보는 다음과 같다.

```text
- YouTube
- 블로그
- Article
- Learning Website
- 내부 문서
- 파일
- 이미지
- 본문 콘텐츠
```

외부 웹/YouTube 콘텐츠는 저작권과 약관 위험을 피하기 위해 원문을 새 창으로 여는 방식을 우선한다.

### 13.2.7 목표물 예시

크리에이터는 콘텐츠를 보고 학습자가 만들거나 수행할 수 있는 목표물 예시를 제시한다.

핵심 질문은 다음과 같다.

```text
이 콘텐츠를 보고 학습자가 만들거나 수행할 수 있는 것은 무엇인가요?
```

예시는 다음과 같다.

```text
- 독자 정의 문장 만들기
- F코드 전환 녹음하기
- Todo 앱 기능 하나 구현하기
- 작은 파우치 v1 만들기
- 영어 주문 대화 녹음하기
```

목표물 예시는 콘텐츠를 단순 이해에서 끝내지 않고, 학습자가 실제로 할 수 있는 결과로 바꾸는 장치다.

### 13.2.8 필요한 스킬 후보

크리에이터는 스킬까지 제시한다. 다만 크리에이터가 제시하는 스킬은 확정값이 아니라 후보다.

```text
크리에이터가 제시하는 스킬 = 추천 후보
학습자가 선택한 스킬 = 실제 학습진행 스킬
AI가 보정한 스킬 = 콘텐츠/목표물 기반 보조 후보
```

이 원칙은 반드시 유지한다. LearnCosmos의 학습 주체는 학습자이기 때문이다.

스킬 후보 입력 예시는 다음과 같다.

```text
[핵심 스킬]
- 독자 페르소나 정의
- 글의 목적 한 문장 정리

[보조 스킬]
- 독자의 문제 찾기
- 제목 후보 만들기

[선택 스킬]
- 글감 분류하기
- 발행 채널에 맞게 톤 조정하기
```

스킬 후보 필드는 다음과 같다.

| 필드 | 설명 |
|---|---|
| 스킬명 | 학습자가 반복할 수 있는 구체 행동 |
| 스킬 유형 | 핵심 / 보조 / 선택 |
| 관련 목표물 | 어떤 목표물을 위해 필요한지 |
| 관찰 근거 | 콘텐츠의 어떤 부분에서 나온 스킬인지 |
| 반복 방법 | 어떻게 연습하면 되는지 |
| 결과물 예시 | 무엇을 남기면 되는지 |
| 흔한 막힘 | 학습자가 자주 어려워할 부분 |

### 13.2.9 반복 탐험 가이드

크리에이터는 학습자가 어떤 행동을 반복하면 좋은지 안내한다.

핵심 질문은 다음과 같다.

```text
학습자가 어떤 행동을 반복하면 좋을까요?
```

예시는 다음과 같다.

```text
독자 후보 3명을 적고,
가장 중요한 독자 1명을 고른 뒤,
그 독자가 읽고 싶어 할 제목을 3개 만들어 보세요.
```

반복 탐험 가이드는 스킬 반복을 구체적인 행동 단위로 바꾸는 역할을 한다.

### 13.2.10 결과물 기준

크리에이터는 학습자가 어떤 결과물이나 증거를 남기면 좋을지 기준을 제시한다.

핵심 질문은 다음과 같다.

```text
학습자가 어떤 결과물이나 증거를 남기면 좋을까요?
```

예시는 다음과 같다.

```text
- 독자 정의 문장
- 제목 후보 목록
- 코드 캡처
- 연습 녹음
- 완성 사진
- 초안 문서
```

결과물 기준은 지점 학습흐름의 결과 정리와 완료 확인에 연결된다.

### 13.2.11 콘텐츠가 개인학습에 들어가는 방식

크리에이터 콘텐츠는 다음 흐름으로 개인학습에 연결된다.

```text
크리에이터 콘텐츠 등록
→ 콘텐츠 검색/추천에 노출
→ 학습자가 학습계획에서 선택
→ 리슨 안에 탐험지점으로 추가
→ 지점 관찰
→ 목표물 발견
→ 필요한 스킬 발견
→ 오늘 반복할 방법 정하기
→ 반복 탐험
```

핵심 정의는 다음과 같다.

```text
크리에이터 콘텐츠
= 개인학습의 탐험지점 후보
```

### 13.2.12 그룹 코스 정의

그룹 코스는 크리에이터 기획에 포함되는 확장 기능이다.

```text
그룹 코스
= 소규모 학원, 모임, 크리에이터가 만든 고정 커리큘럼을
  승인된 학습자에게만 공개하고,
  학습자는 그 안에서 개인별 탐험일지와 결과물을 쌓아가는 제한 공개형 학습경로
```

개인학습은 학습자가 직접 코스를 생성하지만, 소규모 학원/모임/크리에이터는 이미 설계된 커리큘럼을 승인된 학습자에게 제공해야 한다. 그룹 코스는 이 요구를 다룬다.

### 13.2.13 그룹 코스 만들기 흐름

```text
그룹 코스 만들기
→ 기본 정보 입력
→ 코스/리슨 구성
→ 학습콘텐츠 붙이기
→ 탐험지점/연구지점 구성
→ 목표물/스킬 후보 설정
→ 공개 범위 설정
→ 학습자 초대/승인
→ 그룹 코스 오픈
```

그룹 코스 생성 항목은 다음과 같다.

```text
기본 정보
- 그룹 코스 제목
- 소개
- 대상 학습자
- 예상 기간
- 난이도
- 공개 범위

커리큘럼
- 리슨 추가
- 리슨별 탐험지점 추가
- 리슨별 연구지점 템플릿 추가
- 목표물 예시
- 필요한 스킬 후보
- 결과물 기준
```

### 13.2.14 그룹 코스와 개인학습 연결

승인된 학습자는 `개인학습 > 내 학습지도`에서 그룹 코스를 볼 수 있다.

```text
내 학습지도
├─ 개인 코스
├─ 그룹 코스
└─ 완료한 코스
```

그룹 코스도 `오늘 할 일`에 들어온다.

```text
오늘 할 일

그룹 코스: AI 글쓰기 4주 과정
리슨: 독자 정의
지점: 독자 페르소나 작성 자료
```

핵심 원칙은 다음과 같다.

```text
그룹 코스의 커리큘럼은 공통,
학습진행 기록과 결과물은 학습자별로 저장한다.
```

### 13.2.15 피드백과 콘텐츠 개선

크리에이터는 학습자의 피드백을 받아 콘텐츠를 개선할 수 있어야 한다.

피드백 후보는 다음과 같다.

```text
- 완료 후기
- 난이도 반응
- 막힌 지점
- 개선 제안
- 결과물 기준에 대한 의견
- 크리에이터 답변
```

피드백은 단순 리뷰가 아니라 콘텐츠 개선과 학습경험 개선으로 연결되어야 한다.

### 13.2.16 수익화 후순위 원칙

이전 Creator Economy 기획에는 완료율 기반 가격 상한, 크리에이터 등급, 정산 구조가 포함되어 있었다.

다만 LearnCosmos 초기 기준에서는 수익화와 정산을 전면에 두지 않는다.

초기 원칙은 다음과 같다.

1. 먼저 학습 가치가 검증되어야 한다.
2. 크리에이터 콘텐츠는 무료 또는 제한 공개 중심으로 시작한다.
3. 완료율, 피드백, 재사용률을 통해 학습 가치를 확인한다.
4. 수익화, 정산, 가격 상한은 후순위 기획으로 분리한다.
5. 유료화는 검증된 학습경험에 대한 단계적 보상으로 다룬다.

### 13.2.17 설계 원칙

1. 크리에이터는 단순 강의 판매자가 아니다.
2. 크리에이터는 학습경험 설계자다.
3. 크리에이터 콘텐츠는 개인학습의 탐험지점 후보다.
4. 크리에이터가 제시하는 스킬은 확정값이 아니라 후보다.
5. 실제 학습진행 스킬은 학습자가 선택, 수정, 추가한다.
6. AI가 보정한 스킬은 보조 후보로만 사용한다.
7. 그룹 코스는 승인된 학습자에게만 열리는 고정 커리큘럼이다.
8. 그룹 코스의 커리큘럼은 공통이지만 기록과 결과물은 학습자별로 저장한다.
9. 피드백은 콘텐츠 개선으로 연결되어야 한다.
10. 수익화는 학습 가치가 검증된 뒤 단계적으로 적용한다.
11. 크리에이터 기능은 1차 MVP가 아니라 P2 확장 기획으로 관리한다.

## 13.3 학습 안전 게이트 기준

학습 안전 게이트는 LearnCosmos의 학습 입력이 저장되기 전에 학습 목적에 맞는지, 위험하거나 부적절한 내용은 아닌지 1차로 검사하는 공통 안전 레이어다.

이 기준은 기존 LearnWeaver에서 구현해 둔 Safety Gate 데이터와 구조를 계승한다. 신규로 처음부터 다시 설계하지 않고, 기존 `backend/internal/domain/safety`, `moderation_rules`, `moderation_logs`, rule import/검수 데이터, super-admin safety 로그 화면, AI output observation 기준을 LearnCosmos 기준으로 재사용한다.

### 13.3.1 정의

```text
학습 안전 게이트
= 사용자의 학습 입력이 저장되기 전에
  학습 목적에 맞는지, 위험하거나 부적절한 내용은 아닌지
  rule 기반으로 1차 검사하는 공통 안전 레이어
```

학습 안전 게이트는 단순 욕설 필터가 아니다. LearnCosmos의 학습 흐름을 보호하기 위한 입력 검증 장치다.

적용 대상은 다음과 같다.

```text
- 교육 목적이 약한 입력
- 학습과 무관한 목표
- 위험한 행동 지시
- 부적절한 관찰 기록
- 부적절한 질문/답변
- 부적절한 반복 기록
- 부적절한 결과물 설명
- 부적절한 자기평가 입력
- AI 출력물의 위험 후보 관찰
```

### 13.3.2 기본 원칙

1. 사용자 자유 입력은 저장 전 검사한다.
2. 학습 목적이 명확한 입력은 allow한다.
3. 학습 목적이 약하거나 애매한 입력은 soft_warn으로 재작성 유도한다.
4. 명확히 부적합한 입력은 block한다.
5. 원문 입력은 moderation log에 저장하지 않는다.
6. 입력 원문 대신 hash와 metadata만 저장한다.
7. AI output은 초기에는 차단하지 않고 log-only로 관찰한다.
8. 커뮤니티/크리에이터 공개 입력은 후속 확장 대상으로 둔다.
9. 기존 LearnWeaver의 Safety Gate 구현 데이터와 rule 체계를 우선 재사용한다.
10. 과도한 차단보다 학습 목적에 맞게 다시 쓰도록 안내하는 UX를 우선한다.

### 13.3.3 기존 LearnWeaver 구현 자산 계승

LearnCosmos는 다음 LearnWeaver 구현 자산을 계승한다.

| 자산 | 계승 기준 |
|---|---|
| `backend/internal/domain/safety` | 공통 safety service 구조 재사용 |
| `moderation_rules` | 기존 rule 기반 판정 데이터 재사용 |
| `moderation_logs` | 원문 없이 hash와 metadata를 남기는 로그 구조 재사용 |
| `Service.Moderate` | 판정 중심 API로 재사용 |
| `Service.Enforce` | 저장 전 판정 + 로그 기록 경로로 재사용 |
| `/api/v1/safety/moderate` | 사용자 사전 검사 API로 재사용 |
| super-admin safety logs | 운영자 확인 화면으로 재사용 |
| reviewed rule import 데이터 | 검수 완료된 rule만 반영하는 정책 유지 |
| AI output observation 기준 | AI 출력물은 우선 log-only 관찰 기준 유지 |

기존 LearnWeaver의 safety 데이터는 새 LearnCosmos 기준에서 초기 운영 데이터로 활용한다. 단, 서비스명과 사용자 안내 문구는 LearnCosmos 기준으로 바꾼다.

### 13.3.4 판정 정책

판정 action은 다음 세 가지를 기본으로 한다.

| action | 의미 | 처리 |
|---|---|---|
| allow | 저장 가능 | 기존 흐름 유지 |
| soft_warn | 학습 목적이 약하거나 애매함 | 초기에는 저장하지 않고 재작성 유도 |
| block | 명확히 부적합 | 저장/생성 차단 |

초기 연결 API에서는 soft_warn도 저장하지 않고 재작성을 유도한다. 개인 기록에서 soft warning 후 저장 허용은 후속 UX에서 별도로 검토한다.

### 13.3.5 사용자 안내 문구

기본 차단 메시지는 다음 기준을 따른다.

```text
이 내용은 학습 목적과 맞지 않을 수 있어요.
학습 목표나 과제 형태로 바꿔서 다시 작성해 주세요.
```

이 문구는 사용자를 비난하지 않고, 입력을 학습 목표나 과제 형태로 바꾸도록 돕는 안내 문구다.

### 13.3.6 지점 학습흐름 v2와의 연결

학습 안전 게이트는 지점 학습흐름 v2의 자유 입력 저장 전에 적용한다.

| 학습 단계 | 검사 대상 입력 |
|---|---|
| 지점 관찰 | 관찰 기록, 목표 찾기, 스킬 찾기 입력 |
| 스킬 반복 | 질문하고 해답찾기, 반복 기록, 자기평가 입력 |
| 결과 정리 | 결과물 제목, 설명, 제작 과정, 배운 점, 어려운 점 |
| 완료 확인 | 결과물 자기평가, 목표 달성 여부, 다음 보완점 |

즉, 학습 안전 게이트는 별도 부가기능이 아니라 학습흐름의 모든 자유 입력 저장 전 검사 레이어다.

### 13.3.7 Phase 1 계승 범위

기존 LearnWeaver Phase 1 Safety Gate는 다음 영역에 적용되었다.

```text
- 목표 시작
- 목표 인터뷰
- 코스 초안 생성
- 지점 관찰 기록 생성/수정
- frontend 공통 safety error 안내
- super-admin read-only moderation logs 화면
```

LearnCosmos 초기 기준에서는 이 범위를 그대로 계승한다.

### 13.3.8 Phase 2 확장 범위

기존 LearnWeaver Phase 2 계획은 지점 학습 기록 전반으로 안전 게이트를 확장하는 것이다.

LearnCosmos에서는 다음 입력을 확장 적용 대상으로 본다.

```text
- 탐험 목표 / 목표물 발견 입력
- 탐험일지 / journal 입력
- 질문 등록 / 수정
- 사용자 답변
- 연습 / 활동 기록
- 결과물 제목 / 설명
- 보조자료 제목 / 설명 / 링크 메모
- 자기평가 자유 입력
- 연구자료 제목
- 연구자료 본문 텍스트
- 학습대상자료 첨부 제목 / 설명 / 파일명
- 직접 추가 URL 제목 / 설명
- content create/update 메타데이터
```

커뮤니티 공개 피드, 크리에이터 공개 입력, 이미지/영상 파일 본문 moderation, 첨부 파일 본문 OCR/문서 파싱 moderation은 후속 확장으로 둔다.

### 13.3.9 AI output 관찰 기준

AI 출력물은 사용자 입력과 다르게 처리한다.

초기 기준에서는 AI output을 즉시 차단하지 않고, 현재 학습 흐름을 막지 않는 log-only 관찰 대상으로 둔다.

대상 target_type은 다음과 같다.

```text
- ai_goal_interview_output
- ai_course_draft_output
- ai_point_summary_output
- ai_point_question_output
- ai_point_feedback_output
- ai_point_self_evaluation_output
```

AI output moderation 결과가 soft_warn 또는 block이어도 초기에는 사용자 요청을 실패시키지 않는다. 원문 출력은 저장하지 않고, hash, target, route, matched rule, metadata만 운영 확인 대상으로 삼는다.

### 13.3.10 운영 관찰 기준

AI output과 safety log는 운영자가 다음 기준으로 관찰한다.

| 위험도 | 기준 | 후속 판단 |
|---|---|---|
| 낮음 | 24시간 기준 soft_warn/block 1\~2건, 반복 없음 | 관찰 유지 |
| 주의 | 동일 target_type 또는 matched rule이 3건 이상 반복 | false-positive 또는 rule tuning 검토 |
| 경고 | 동일 target_type block 5건 이상 또는 soft_warn+block 비율 5% 이상 | 운영 리포트 / 집계 UI / export 검토 |
| 심각 | 사용자에게 보여주기 어려운 AI 출력 반복, 특정 기능 block 비율 10% 이상 | 마스킹, 재생성, 학습자 경고, feature flag 제한 검토 |

### 13.3.11 로그와 개인정보 원칙

학습 안전 게이트는 운영 검토를 위해 로그를 남기되, 원문 저장은 하지 않는다.

원칙은 다음과 같다.

```text
- 원문 입력 저장 금지
- matched text 저장 금지
- prompt 원문 저장 금지
- input_text_hash 저장
- target_type 저장
- route 저장
- risk_type 저장
- action 저장
- matched_rule_id 저장
- locale 저장
- metadata 저장
```

이 원칙은 LearnWeaver 구현 기준을 그대로 계승한다.

### 13.3.12 rule 관리 원칙

rule은 대량 import하지 않는다. 검수 완료된 항목만 반영한다.

기존 LearnWeaver 기준을 따라 다음 절차를 유지한다.

```text
외부 후보 수집
→ candidates JSONL 생성
→ 검수 CSV 작성
→ review_decision=approve 확인
→ import_ready=true 확인
→ dry-run
→ 중복 확인
→ apply
→ moderation_rules 반영
```

검수되지 않은 외부 금칙어 후보는 바로 운영 rule에 넣지 않는다. false positive를 줄이기 위해 사람 검수를 거친다.

### 13.3.13 커뮤니티/크리에이터 확장 기준

커뮤니티와 크리에이터 기능은 P2 확장 기획이다. 따라서 해당 입력의 안전 게이트도 후속 확장으로 둔다.

다만 공개 입력이 포함되므로, 실제 공개 기능을 열기 전에는 반드시 safety gate를 연결한다.

확장 대상은 다음과 같다.

```text
- 커뮤니티 이름 / 소개 / 운영 규칙
- 커뮤니티 게시글 / 질문 / 결과물 공유
- 커뮤니티 댓글 / 피드백
- 크리에이터 프로필 / 소개
- 크리에이터 콘텐츠 제목 / 설명
- 목표물 예시
- 스킬 후보
- 반복 가이드
- 결과물 기준
- 그룹 코스 제목 / 소개 / 커리큘럼 설명
```

### 13.3.14 최종 기준

LearnCosmos의 학습 안전 게이트는 학습자의 표현을 억압하는 장치가 아니라, 입력을 학습 목적에 맞게 정리하도록 돕는 보호 장치다.

최종 기준은 다음과 같다.

```text
학습 안전 게이트는
사용자 입력을 단순 차단하는 필터가 아니라,
학습 목표, 스킬 반복, 질문, 결과물, 자기평가가
교육적 흐름 안에서 유지되도록 돕는 안전 레이어다.
```

## 13.4 학습 설계 패턴 계승 기준

LearnCosmos는 기존 LearnWeaver에서 구현한 리슨 패턴, 리슨 명세, 추천 검색 명세 데이터를 `학습 설계 패턴`으로 재정의해 계승한다.

학습 설계 패턴은 사용자의 학습 목표를 행성, 지역, 지점 구조로 바꾸고, 각 지점이 어떤 목표, 스킬, 반복, 결과물 흐름을 가져야 하는지 안내하는 데이터 기반 설계 기준이다.

### 13.4.1 정의

```text
학습 설계 패턴
= 사용자의 학습 목표를
  행성·지역·지점 구조와
  지점 학습흐름, 추천 콘텐츠 기준으로 바꾸기 위한
  데이터 기반 학습 설계 기준
```

서비스 기획 용어는 `학습 설계 패턴`으로 통일한다. 구현 내부 용어는 기존 LearnWeaver의 `curriculum_patterns`, `curriculum_pattern_embeddings`, `recommendation_search_spec`를 유지할 수 있다.

### 13.4.2 기존 LearnWeaver 구현 자산 계승

LearnCosmos는 다음 LearnWeaver 구현 자산을 계승한다.

| 기존 구현 자산 | LearnCosmos 기준 역할 |
|---|---|
| curriculum_patterns | 학습 설계 패턴 원본 데이터 |
| curriculum_pattern_embeddings | 학습 목표와 패턴을 매칭하는 검색 데이터 |
| pattern_key / subpattern_key | 도메인·목표 유형별 설계 패턴 식별자 |
| stage_rules | 지점 진행 규칙 |
| recommended_sequence | 지역/지점 학습 순서 기준 |
| bad_patterns | 잘못된 리슨/지점 흐름 방지 기준 |
| guidance | 코스 생성 시 패턴 기반 안내문 |
| recommendation_search_spec_template | 추천 콘텐츠 검색 명세 템플릿 |
| recommendation_search_spec | 실제 리슨/지점별 추천 검색 기준 |

### 13.4.3 기획 용어와 구현 용어 분리

기획 문서와 사용자-facing 설명에서는 다음 용어를 사용한다.

| 구현 용어 | 기획 용어 |
|---|---|
| curriculum_patterns | 학습 설계 패턴 |
| curriculum_pattern_embeddings | 학습 설계 패턴 검색/매칭 데이터 |
| lesson pattern | 지역/지점 구성 패턴 |
| stage_rules | 지점 진행 규칙 |
| recommended_sequence | 학습 경로 순서 |
| bad_patterns | 잘못된 학습흐름 방지 기준 |
| recommendation_search_spec_template | 추천 콘텐츠 검색 명세 템플릿 |
| recommendation_search_spec | 리슨/지점별 추천 검색 명세 |

내부 코드와 DB에서는 기존 명칭을 유지하되, 문서와 기획에서는 LearnCosmos의 세계관과 학습흐름에 맞게 해석한다.

### 13.4.4 학습 설계 패턴의 목적

학습 설계 패턴의 목적은 다음과 같다.

1. 사용자의 막연한 학습 목표를 구체적인 행성/지역/지점 구조로 바꾼다.
2. 도메인별로 적절한 학습 순서를 제안한다.
3. 지점별 목표, 스킬, 반복, 결과물 흐름을 안정적으로 만든다.
4. 잘못된 리슨 흐름이나 너무 일반적인 코스 생성을 줄인다.
5. 추천 콘텐츠 검색에 필요한 검색 의도와 필터 기준을 함께 만든다.
6. 코드 보정만으로 해결하던 리슨 생성 품질 문제를 데이터 기반으로 관리한다.
7. 새로운 사용자 입력과 QA 결과를 다시 패턴 데이터로 축적할 수 있게 한다.

### 13.4.5 코스 생성에서의 활용 흐름

LearnCosmos의 코스 생성에서는 학습 설계 패턴을 다음 흐름으로 사용한다.

```text
사용자 학습 목표 입력
→ 학습 안전 게이트 검사
→ 목표/도메인/학습 유형 분석
→ 학습 설계 패턴 검색
→ 적절한 pattern/subpattern 선택
→ 행성/지역/지점 구조 생성
→ 지점별 목표/스킬/반복/결과물 흐름 보정
→ 리슨/지점별 추천 검색 명세 생성
→ 코스 초안 저장
→ 사용자가 검토/수정
```

이 흐름에서 학습 설계 패턴은 LLM이 임의로 코스 구조를 만드는 것을 줄이고, 데이터 기반의 안정적인 설계 기준을 제공한다.

### 13.4.6 지점 학습흐름 v2와의 연결

학습 설계 패턴은 지점 학습흐름 v2와 연결되어야 한다.

| 지점 학습흐름 v2 | 학습 설계 패턴에서 제공할 수 있는 기준 |
|---|---|
| 지점 관찰 | 이 지점에서 관찰해야 할 자료 성격과 핵심 질문 |
| 목표 찾기 | 지점 완료 시 얻어야 할 목표물/성과 |
| 스킬 찾기 | 목표 달성에 필요한 핵심/보조/선택 스킬 후보 |
| 스킬 반복 | 반복 방식, 연습 순서, 수행 기준 |
| 질문하고 해답찾기 | 자주 막히는 지점과 탐구 질문 후보 |
| 자기평가 | 이해/수행/발전 여부를 확인하는 질문 |
| 결과 정리 | 결과물 또는 증거의 형태 |
| 완료 확인 | 완료 조건과 다음 보완점 기준 |

따라서 학습 설계 패턴은 단순히 리슨 제목을 만드는 데이터가 아니라, 지점 학습 경험 전체를 구성하는 설계 데이터다.

### 13.4.7 추천 콘텐츠 검색 명세와의 연결

기존 LearnWeaver에서는 리슨 생성 시점에 리슨별 추천 검색 명세를 생성하고 저장하는 구조가 구현되어 있다. LearnCosmos는 이 구조를 계승한다.

추천 검색 명세의 핵심 필드는 다음과 같다.

| 필드 | 역할 |
|---|---|
| primary_query | 외부/내부 검색에 우선 사용할 검색어 |
| intent | tutorial, lecture, practice, example, checklist, reference, course 등 검색 의도 |
| must_include | 반드시 포함되어야 할 핵심 토큰 |
| nice_to_have | 있으면 가산할 보조 토큰 |
| avoid | 감점 또는 제외할 광고/판매/단계 부적합 신호 |
| content_types | video, article, course, document 등 선호 자료 유형 |
| language | ko 또는 en |
| stage_role | 해당 리슨/지점의 단계 역할 |
| source | generated, pattern_template, fallback, manual 등 명세 출처 |

이 명세는 추천 검색 시점에 LLM을 다시 호출하지 않고, YouTube, Naver Blog, 내부 lexical/vector 검색과 코드 랭킹에서 사용한다.

### 13.4.8 추천 품질 문제와 학습 설계 문제의 분리

학습 설계 패턴은 리슨/지점 구조를 보정하는 데이터다. 추천 콘텐츠 필터링 문제를 학습 설계 패턴만으로 해결하려고 하면 안 된다.

구분 기준은 다음과 같다.

| 문제 유형 | 예 | 주 적용 위치 |
|---|---|---|
| 학습 설계 패턴 문제 | 목표는 목공예인데 리슨 단계가 너무 일반적임 | curriculum pattern catalog / seed / embedding |
| 추천 콘텐츠 문제 | 목공예 리슨에서 요리 블로그가 추천됨 | 추천 query / filter / ranking |
| 목표 인터뷰 문제 | 취미 목표가 `배우기` 같은 약한 목표로 제안됨 | goal service / goal interview |

이 구분은 유지한다.

### 13.4.9 데이터 보강 절차

새로운 학습 패턴을 발견하면 다음 절차로 보강한다.

```text
1. 실제 사용자 생성, 운영 QA, 공개 강의/커리큘럼 분석, 실패 로그 분석에서 패턴 후보 수집
2. 목표/코스명, 확정 목표, 언어, 도메인, 목표 유형 기록
3. 현재 생성 리슨과 문제점 기록
4. 원하는 리슨 흐름 기록
5. stage rules, completion criteria, bad patterns, trigger keywords, query terms 기록
6. code catalog 보강
7. seed JSON 재생성
8. DB seed upsert
9. pattern embedding backfill
10. preview 검증
11. 실제 코스 생성 QA
12. 추천 필터와 분리해야 할 후속 작업 기록
```

seed JSON은 직접 수정하지 않는다. 패턴 원본은 code catalog를 기준으로 하고, seed JSON은 export 결과물로 취급한다.

### 13.4.10 운영 원칙

학습 설계 패턴 운영 원칙은 다음과 같다.

1. 패턴은 사용자 확정 목표보다 우선하지 않는다.
2. domain과 goal_type이 어긋나는 guidance를 prompt에 넣지 않는다.
3. 콘텐츠 추천용 embedding과 학습 설계 패턴 embedding은 별도 경로로 유지한다.
4. BYOK LLM key는 pattern embedding에 사용하지 않는다.
5. 추천 품질 문제와 리슨 생성 패턴 문제를 섞지 않는다.
6. code routing은 완전히 제거하지 않고 최소 guard와 fallback으로 유지한다.
7. 패턴 데이터는 운영 QA와 실제 사용자 실패 사례를 통해 지속적으로 보강한다.
8. LearnWeaver의 기존 ready embedding과 seed/upsert/backfill 절차를 LearnCosmos 초기 데이터로 활용한다.

### 13.4.11 LearnCosmos 기준 최종 의미

학습 설계 패턴은 LearnCosmos에서 다음 역할을 한다.

```text
학습 설계 패턴은
사용자의 학습 목표를 행성·지역·지점 구조로 변환하고,
각 지점이 목표·스킬·반복·결과물·완료 기준을 갖도록 돕는
데이터 기반 학습 설계 자산이다.
```

이 기준에 따라 LearnCosmos는 기존 LearnWeaver의 리슨 패턴과 리슨 명세 데이터를 버리지 않고, 학습 설계 패턴이라는 상위 개념으로 계승한다.

## 13.5 사용자 계정 및 관리자 운영 기준

LearnCosmos의 사용자 계정 관리는 단순한 가입/로그인 관리에서 끝나지 않는다. 사용자 본인은 자신의 학습 상태, AI 사용량, 포인트, 결과물을 확인할 수 있어야 하며, 관리자는 서비스 운영과 학습 활성도를 판단할 수 있는 요약 지표와 관리 기능을 확인할 수 있어야 한다.

단, 관리자는 사용자의 비공개 학습 기록 원문, BYOK API Key 원문, Safety Gate 입력 원문, 내부 프롬프트 원문을 기본적으로 열람하지 않는다.

### 13.5.1 사용자 계정 기본 기준

사용자 계정의 기본 식별 기준은 이메일이 아니라 다음 조합을 따른다.

```text
social_accounts.provider + social_accounts.provider_id
```

이메일은 보조 정보로 사용한다. 카카오처럼 이메일이 없는 소셜 계정도 허용할 수 있어야 하며, 이 경우 `users.email = NULL`과 보조 표시값을 사용할 수 있다.

계정 탈퇴는 즉시 완전 삭제가 아니라 soft withdrawal을 기본으로 한다.

```text
users.status = withdrawn
```

같은 소셜 계정으로 재로그인하면 운영 정책에 따라 active 상태로 복구할 수 있다.

### 13.5.2 로그인 후 Gate 순서

사용자가 로그인한 뒤에는 다음 순서로 진입 조건을 확인한다.

```text
OAuth 또는 demo login 성공
→ 언어 설정 확인
→ 필수 약관 동의 확인
→ 알파/베타 접근권 확인
→ 대시보드 또는 요청 목적지 진입
```

기본 기준은 다음과 같다.

1. 언어 설정이 없으면 언어 설정 화면으로 이동한다.
2. 필수 약관 동의가 없으면 약관 동의 화면으로 이동한다.
3. 접근권이 없으면 초대코드 입력 화면으로 이동한다.
4. `/dashboard/settings/profile`은 접근권이 없어도 계정 탈퇴를 위해 접근 가능해야 한다.
5. 학습 기능 API에는 필요한 경우 접근권 middleware를 붙인다.

### 13.5.3 사용자 본인이 확인할 수 있는 데이터

사용자는 자신의 학습 상태와 AI 사용 상태를 확인할 수 있어야 한다.

| 구분 | 사용자 확인 데이터 |
|---|---|
| 계정 정보 | 닉네임, 프로필 이미지, UI 언어, 학습 생성 언어, 소셜 로그인 provider |
| 접근 상태 | 약관 동의 상태, 알파/베타 접근권 상태 |
| 학습 요약 | 생성한 행성/코스 수, 진행 중 코스 수, 완료 코스 수 |
| 완료율 | 내 코스 완료율, 내 지점 완료율 |
| 최근 활동 | 최근 학습일, 최근 코스 생성일, 최근 결과물 작성일 |
| 학습 기록 | 질문하고 해답찾기, 반복 기록, 자기평가 |
| 결과물 | 내가 제출한 결과물, 링크, 파일, 캡처, 녹음/녹화 |
| AI 포인트 | 현재 잔액, 사용량, 건별 사용 내역 |
| BYOK | provider, model, 토큰 사용량, 예상 비용, 최근 사용일 |
| 계정 관리 | 언어 설정, 약관 확인, 계정 탈퇴 |

사용자 화면의 핵심 지표는 다음과 같다.

```text
내 코스 생성 수
내 진행 중 코스 수
내 완료 코스 수
내 코스 완료율
내 지점 완료율
내 결과물 수
내 질문 수
내 반복 기록 수
최근 학습일
AI 포인트 사용량
BYOK 토큰 사용량
BYOK 예상 비용
```

### 13.5.4 사용자용 AI 포인트 사용 내역

사용자는 본인의 AI 포인트 잔액과 건별 사용 내역을 확인할 수 있어야 한다.

요약 카드는 다음과 같다.

```text
AI 포인트
- 현재 잔액
- 이번 달 사용 포인트
- 총 사용 포인트
- 최근 사용일
```

건별 리스트 필드는 다음과 같다.

| 필드 | 설명 |
|---|---|
| 사용일시 | AI 기능을 사용한 시각 |
| 기능 | 코스 생성, 목표 인터뷰, 지점 요약, 질문 생성, 피드백, 자기평가 등 |
| 대상 | 코스명, 지점명, 결과물명 등 |
| 사용 모델 | 사용한 모델명 |
| 사용 포인트 | 차감된 포인트 |
| 처리 상태 | 성공, 실패, 취소, 차감 없음 |
| 메모 | 실패 사유 또는 시스템 메시지 요약 |

### 13.5.5 사용자용 BYOK 사용 내역

BYOK는 사용자가 직접 등록한 API Key로 AI를 호출하는 방식이다. 이 경우 LearnCosmos 포인트가 아니라 사용자의 외부 provider 계정에서 비용이 발생할 수 있으므로, 사용자는 건별 토큰 사용량과 예상 비용을 확인할 수 있어야 한다.

요약 카드는 다음과 같다.

```text
BYOK 사용량
- 이번 달 호출 수
- 이번 달 입력 토큰
- 이번 달 출력 토큰
- 이번 달 총 토큰
- 이번 달 예상 비용
- 최근 사용일
```

건별 리스트 필드는 다음과 같다.

| 필드 | 설명 |
|---|---|
| 사용일시 | BYOK 호출 시각 |
| 기능 | 코스 생성, 요약, 질문 생성, 피드백 등 |
| 대상 | 코스/지점/결과물 |
| Provider | OpenAI, Anthropic, Google 등 |
| 모델 | 사용 모델 |
| 입력 토큰 | input tokens |
| 출력 토큰 | output tokens |
| 총 토큰 | 입력 + 출력 |
| 예상 비용 | 모델 단가 기준 추정 비용 |
| 비용 기준 | 계산에 사용한 단가 버전 또는 기준일 |
| 상태 | 성공, 실패, 제한, timeout |
| 오류 코드 | 사용자에게 보여줄 stable error_code |

BYOK 예상 비용은 실제 청구액이 아니라 참고값이다.

```text
예상 비용은 provider 공개 단가와 기록된 token 사용량을 기준으로 계산한 참고값입니다.
실제 청구액은 provider 계정의 과금 정책, 할인, 환율, 세금, 캐시 정책에 따라 달라질 수 있습니다.
```

### 13.5.6 관리자가 확인할 수 있는 사용자 데이터

관리자는 사용자별 운영 상태와 학습 활성도, AI 사용량을 확인할 수 있어야 한다.

| 구분 | 관리자 확인 데이터 |
|---|---|
| 사용자 기본 | user_id, 닉네임, 가입일, 상태, role, provider |
| 접근권 | alpha_access_granted_at, 초대코드 사용 여부, 약관 동의 상태 |
| 학습 활동 | 코스 생성 수, 진행 중 코스 수, 완료 코스 수, 코스 완료율 |
| 지점 활동 | 전체 지점 수, 완료 지점 수, 지점 완료율, 최근 지점 기록일 |
| 결과물 활동 | 결과물 수, 최근 결과물 작성일 |
| 질문/반복 | 질문 수, 반복 기록 수, 자기평가 수 |
| AI 포인트 | 잔액, 지급량, 사용량, 최근 사용일 |
| BYOK 통계 | BYOK 활성 여부, 호출 수, 입력/출력 토큰, 예상 비용 |
| 오류/실패 | 실패 건수, stable error_code, timeout, provider 제한 |
| 데모 계정 | 배정 대상, 데모 코드 상태, 최초 사용일, 최근 사용일, 만료일 |
| 운영 조치 | 계정 비활성화, 데모 코드 재발급, 데모 데이터 purge-preview/purge |

### 13.5.7 관리자가 확인할 수 없는 데이터

```text
- 지점 완료율
- 결과물 수
- AI 사용량
- 포인트 사용량
- BYOK 토큰 사용량
- 예상 비용
- 오류 코드
```


### 13.5.9 초대 코드 관리 기준

초대 코드는 실제 사용자의 가입과 학습 기능 접근권을 관리하기 위한 장치다.

```text
초대 코드 = 실제 사용자 온보딩 / 베타 접근권 관리
```

운영자는 슈퍼관리자에서 초대 코드를 발급하고, 발송 대상 메모와 운영 메모를 남길 수 있어야 한다.

| 항목 | 기준 |
|---|---|
| 사용자 | 실제 Google/Kakao 등 소셜 로그인 사용자 |
| 계정 생성 | 사용자가 직접 가입 |
| 코드 귀속 | 사전 이메일 귀속 없음 |
| 식별 기준 | provider + provider_id + users.id |
| 기본 사용 횟수 | 1회 |
| 관리 기능 | 발급, 만료일 설정, max_uses 설정, 회수, 사용 이력 확인 |
| 사용 후 처리 | users.alpha_access_granted_at 설정 |

초대 코드는 실제 베타 사용자 모집과 장기 사용자 전환 분석에 사용한다.

### 13.5.10 데모 계정 관리 기준

데모 계정은 외부 시연, QA, 임시 체험을 위한 운영 계정이다.

```text
데모 계정 = 시연 / QA / 임시 체험용 학습자 계정
```

기본 원칙은 다음과 같다.

```text
데모 계정은 원칙적으로 1인 1계정으로 발급한다.
```

여러 사람이 하나의 데모 계정을 공유하면 코스 생성 수, 완료율, AI 포인트 사용량, BYOK 사용량, 결과물 기록이 섞이므로 기본 운영 방식으로 사용하지 않는다.

다만 공개 체험이나 화면 시연을 위한 별도 샘플 계정은 만들 수 있다. 이 경우 데이터 저장, AI 호출, 개인정보 입력을 제한하고 주기적으로 초기화한다.

데모 계정 기본 기준은 다음과 같다.

| 항목 | 기준 |
|---|---|
| 권한 | learner |
| 기능 | 일반 학습자와 같은 기능 사용 가능 |
| 기본 포인트 | 300pt |
| 로그인 방식 | 데모 전용 로그인 코드 |
| 코드 저장 | 원문 1회 표시, DB에는 hash 저장 |
| 계정 추적 | demo_accounts 테이블 |
| 운영 기능 | 생성, 배정, 만료, 비활성화, 코드 재발급, purge-preview, purge |
| 데이터 정리 | 데모 계정의 학습 데이터만 일괄 삭제 가능 |

### 13.5.11 초대 코드와 데모 계정의 구분

| 구분 | 초대 코드 | 데모 계정 |
|---|---|---|
| 목적 | 실제 사용자 접근권 관리 | 시연/테스트/체험 |
| 사용자 | 실제 가입자 | 슈퍼관리자가 만든 데모 사용자 |
| 로그인 | 소셜 로그인 후 코드 입력 | 데모 코드 로그인 |
| 데이터 | 실제 사용자 학습 데이터 | 테스트용 학습 데이터 |
| 분석 | 전환율, 장기 학습 분석 | 피드백, QA, 시연 분석 |
| 정리 | 접근권 만료/회수 | 학습 데이터 purge 가능 |
| 기본 운영 | 베타 모집 | 외부 시연/QA |

최종 정책은 다음과 같다.

```text
초대 코드와 데모 계정은 분리 운영한다.
초대 코드는 실제 사용자의 가입과 접근권 관리에 사용한다.
데모 계정은 외부 시연, QA, 임시 체험을 위한 운영 계정으로 사용한다.
두 기능은 슈퍼관리자에서 함께 관리하되, 사용자 데이터와 데모 데이터는 구분한다.
```

### 13.5.12 학습 활동 지표 계산 기준

```text
코스 완료율
= 완료 코스 수 / 생성 코스 수 × 100

지점 완료율
= 완료 지점 수 / 전체 지점 수 × 100

학습 활성 사용자
= 최근 N일 안에 지점 기록, 질문, 반복 기록, 결과물 중 하나 이상을 남긴 사용자

코스 생성 사용자
= 최근 N일 안에 코스/행성을 1개 이상 생성한 사용자

완료 경험 사용자
= 완료 코스 또는 완료 지점을 1개 이상 가진 사용자
```

데모 계정에서는 다음 지표를 별도로 본다.

```text
데모 사용 여부
= 최초 로그인 시각이 있는가

데모 학습 여부
= 코스 생성 수 또는 지점 기록 수가 1개 이상인가

데모 완료 경험
= 완료 지점 또는 완료 코스가 1개 이상인가
```

### 13.5.13 관리자 이벤트 포인트 지급 기준

관리자는 사용자별로 이벤트 포인트를 지급할 수 있어야 한다. 이벤트 포인트는 베타 테스트 참여, 피드백 제공, 오류 제보, 학습 이벤트, 운영 보상 등 명확한 근거가 있는 경우에만 지급한다.

이벤트 포인트 지급은 단순 수동 조정이 아니라 운영 기록이 남는 관리 행위로 본다. 따라서 포인트 지급 시 지급 사유와 근거 메모를 반드시 남긴다.

#### 지급 가능 사유

```text
- 베타 테스트 참여 보상
- 서비스 오류 제보 보상
- 설문/인터뷰 참여 보상
- 학습 이벤트 참여 보상
- 운영자가 승인한 특별 체험 포인트
- 데모/QA 목적의 테스트 포인트 지급
- 포인트 차감 오류 보정
- 기타 운영상 필요한 보상
```

#### 관리자 지급 입력 항목

| 항목 | 기준 |
|---|---|
| 대상 사용자 | user_id 또는 사용자 검색으로 선택 |
| 지급 포인트 | 양수 포인트 값 |
| 지급 유형 | event_grant / adjustment / compensation / demo_grant 등 |
| 지급 사유 | 짧은 분류값 |
| 근거 메모 | 관리자가 직접 작성하는 필수 메모 |
| 관련 대상 | 선택값: 코스, 지점, 오류 티켓, 이벤트명 등 |
| 사용자 표시 메모 | 사용자에게 노출할 짧은 설명 |
| 관리자 ID | 지급 처리한 관리자 |
| 처리 시각 | 지급 일시 |

#### 사용자에게 보이는 방식

사용자는 자신의 AI 포인트 내역에서 이벤트 포인트 지급 내역을 확인할 수 있어야 한다.

예시는 다음과 같다.

```text
2026-06-22
이벤트 포인트 지급 +100P
사유: 베타 테스트 참여 보상
```

사용자에게는 내부 운영 메모 전체를 노출하지 않는다. 사용자에게는 `사용자 표시 메모` 또는 짧은 지급 사유만 보여준다.

#### 관리자에게 보이는 방식

관리자는 사용자 상세의 포인트 내역에서 다음 정보를 확인할 수 있어야 한다.

```text
- 지급 일시
- 지급 관리자
- 지급 포인트
- 지급 유형
- 지급 사유
- 근거 메모
- 관련 대상
- 사용자 표시 메모
```

#### 운영 원칙

1. 이벤트 포인트 지급은 반드시 관리자 권한에서만 가능하다.
2. 지급 사유와 근거 메모는 필수다.
3. 지급 후 포인트 거래 내역에 기록되어야 한다.
4. 지급 내역은 사용자의 포인트 내역에도 표시되어야 한다.
5. 사용자는 지급 사실과 사용자용 사유를 볼 수 있다.
6. 내부 운영 메모는 관리자에게만 보인다.
7. 지급 취소나 정정이 필요한 경우 원거래를 수정하지 않고 별도 보정 거래로 남긴다.
8. 데모 계정에 지급한 포인트는 데모 계정 purge-preview에서 함께 집계되어야 한다.

#### 데이터 기준

이벤트 포인트 지급은 기존 AI 포인트 지갑/거래 구조를 활용한다.

권장 거래 유형은 다음과 같다.

```text
ai_point_transactions.type = event_grant | adjustment | compensation | demo_grant
```

기존 거래 타입 제약이 있다면, 초기에는 기존 `grant_free`를 사용하되 metadata에 다음 정보를 남긴다.

```json
{
  "grant_reason": "beta_test_reward",
  "admin_note": "베타 테스트 인터뷰 참여 보상",
  "user_visible_note": "베타 테스트 참여 보상",
  "granted_by": "admin_user_id",
  "related_target_type": "event",
  "related_target_id": "optional"
}
```

최종적으로는 이벤트 포인트 지급을 일반 무료 포인트 지급과 구분할 수 있도록 거래 유형 또는 metadata 기준을 명확히 유지한다.

```text
사용자 계정 관리는 가입/로그인 관리에서 끝나지 않는다.
```

## 13.6 추천 품질 고도화 및 LightGBM Ranker 적용 기준

LearnCosmos의 추천 시스템은 초기에는 `검색 명세 + 하이브리드 검색 + rule ranking`을 기본으로 사용한다. 이후 사용자 학습 데이터가 충분히 쌓이면 LightGBM Ranker를 후보 재정렬 모델로 적용한다.

LightGBM Ranker는 추천 후보를 새로 생성하는 모델이 아니라, 이미 수집된 후보를 학습 효과 기준으로 재정렬하는 모델이다.

### 13.6.1 적용 흐름

```text
기본 추천
→ 학습 데이터 수집
→ Ranker 학습
→ 오프라인 검증
→ Shadow Mode
→ 제한 적용
→ 전체 적용
```

운영 적용은 자동으로 진행하지 않는다. 각 단계의 조건이 충족되면 관리자 페이지에서 해당 적용 버튼이 활성화되고, 관리자가 직접 적용한다.

### 13.6.2 관리자 적용 단계

```text
슈퍼관리자 > 추천 모델 관리
├─ 데이터 준비도 확인
├─ 모델 학습
├─ 검증 결과 확인
├─ Shadow Mode 적용
├─ 제한 적용
├─ 전체 적용
└─ 롤백
```

각 단계는 모델 버전 단위로 관리한다.

### 13.6.3 버튼 활성화 기준

| 단계 | 버튼 | 활성화 조건 |
|---|---|---|
| 모델 학습 | 모델 학습 시작 | 최소 학습 데이터 기준 충족 |
| 검증 | 검증 리포트 보기 | 학습 완료 |
| Shadow | Shadow Mode 적용 | 오프라인 검증 기준 통과 |
| 제한 적용 | 제한 적용 | Shadow 기준 통과 |
| 전체 적용 | 전체 적용 | 제한 적용 기준 통과 |
| 롤백 | 이전 버전으로 롤백 | 직전 운영 버전 존재 |

### 13.6.4 제한 적용 기준

제한 적용은 전체 사용자에게 바로 적용하지 않고, 일부 트래픽 또는 일부 사용자 그룹에만 Ranker 결과를 노출하는 단계다.

제한 적용 버튼은 다음 조건을 충족할 때 활성화한다.

```text
- 모델 학습 완료
- 오프라인 검증 통과
- Shadow Mode 최소 기간 충족
- 기존 ranking 대비 NDCG 개선
- 부적합 추천 상위 노출률 증가 없음
- Safety Gate 관련 위험 신호 증가 없음
- 롤백 가능한 이전 버전 존재
```

제한 적용 범위는 관리자가 선택할 수 있다.

```text
- 데모 계정만 적용
- 내부 QA 계정만 적용
- 베타 사용자 10% 적용
- 베타 사용자 25% 적용
- 특정 사용자 그룹 적용
```

### 13.6.5 전체 적용 기준

전체 적용 버튼은 제한 적용 이후 다음 조건을 충족할 때 활성화한다.

```text
- 제한 적용 기간 충족
- 기존 추천 대비 선택률 하락 없음
- 지점 추가율 하락 없음
- 지점 완료율 하락 없음
- 결과물 작성률 하락 없음
- 부적합 처리율 증가 없음
- 오류율/timeout 증가 없음
- 관리자 검토 완료
```

전체 적용은 현재 운영 추천 모델 버전을 교체하는 작업이다. 따라서 전체 적용 시점에는 적용 관리자, 적용 사유, 모델 버전, 이전 버전, 적용 범위를 기록한다.

### 13.6.6 관리자 화면 표시 항목

```text
모델 버전
학습 일시
학습 데이터 기간
학습 데이터 수
추천 요청 group 수
후보 수
NDCG@3
NDCG@5
NDCG@10
기존 rule ranking 대비 개선율
부적합 추천 상위 노출률
선택률
지점 추가율
지점 완료율
결과물 작성률
오류율
현재 적용 상태
적용 가능 버튼
롤백 가능 여부
```

### 13.6.7 모델 적용 상태

```text
draft
→ trained
→ validated
→ shadow
→ limited
→ active
→ rolled_back
```

| 상태 | 의미 |
|---|---|
| draft | 모델 후보 생성 전 |
| trained | 학습 완료 |
| validated | 오프라인 검증 통과 |
| shadow | 실제 노출 없이 비교 기록 중 |
| limited | 일부 사용자/트래픽에 제한 적용 |
| active | 전체 운영 적용 |
| rolled_back | 이전 버전으로 롤백됨 |

### 13.6.8 제한 적용 예시

```text
모델 버전: ranker_2026_07_01_v1
상태: Shadow 통과
제한 적용 가능

[제한 적용] 버튼 활성화

적용 범위:
- 데모 계정
- 내부 QA 계정
- 베타 사용자 10%
```

관리자가 `베타 사용자 10%`를 선택하고 적용하면 해당 범위에만 Ranker 재정렬 결과를 노출한다.

### 13.6.9 전체 적용 예시

```text
모델 버전: ranker_2026_07_01_v1
상태: 제한 적용 통과
전체 적용 가능

[전체 적용] 버튼 활성화
```

관리자가 전체 적용을 누르면 해당 모델이 기본 추천 재정렬 모델이 된다.

### 13.6.10 롤백 기준

다음 상황에서는 즉시 롤백할 수 있어야 한다.

```text
- 추천 클릭률 급감
- 지점 추가율 급감
- 지점 완료율 하락
- 부적합 추천 신고 증가
- 특정 도메인 추천 품질 저하
- 오류율 증가
- 모델 feature 오류 확인
```

롤백은 이전 active 모델 또는 rule ranking 기본값으로 되돌린다.

```text
[이전 모델로 롤백]
[기본 rule ranking으로 롤백]
```

롤백 시에도 관리자 ID, 사유, 롤백 전 모델, 롤백 후 모델을 기록한다.

### 13.6.11 운영 원칙

1. LightGBM Ranker는 추천 후보 생성 모델이 아니라 후보 재정렬 모델이다.
2. 전체 적용 전 반드시 제한 적용 단계를 거친다.
3. 관리자는 조건 충족 여부를 확인하고 버튼으로 적용한다.
4. 조건을 충족하지 않으면 적용 버튼은 비활성화한다.
5. 모든 적용과 롤백은 모델 버전 단위로 기록한다.
6. 추천 품질은 클릭률보다 지점 추가율, 지점 완료율, 결과물 작성률을 더 중요하게 본다.
7. 문제가 생기면 즉시 이전 버전 또는 rule ranking으로 롤백할 수 있어야 한다.

## 13.7 관리자 학습 설계 시뮬레이터 및 템플릿 적용 기준

LearnCosmos는 관리자가 실제 사용자 코스를 직접 수정하기 전에, 임의의 테스트 코스를 생성하여 LLM 기반 코스 초안과 리슨 패턴 명세 보정 결과를 미리 검증할 수 있어야 한다.

이 기능은 단순 테스트 도구가 아니라, 좋은 코스/리슨 설계 템플릿을 축적하고 이후 실제 리슨 생성 시 학습 설계 패턴과 명세 생성에 반영하기 위한 운영 도구다.

### 13.7.1 기능 정의

관리자 학습 설계 시뮬레이터는 관리자가 학습 주제, 수준, 목표, 기간, 선호 자료 유형, 학습 언어, 제외 조건, 원하는 결과물을 입력하면 LLM이 코스 초안과 지점 구조를 생성하고, 시스템이 이를 학습 설계 패턴 기준으로 보정해 보여주는 기능이다.

기본 흐름은 다음과 같다.

관리자 입력 → LLM 코스 초안 생성 → 리슨 패턴 명세 보정 → 추천 검색 명세 생성 → 추천 코스/지점 구조 미리보기 → 관리자 검토 → 폐기 또는 저장 → 공식 템플릿 등록 → 실제 리슨 생성 시 참조

### 13.7.2 관리자 메뉴 위치

슈퍼관리자 > 학습 설계 관리 아래에 다음 메뉴를 둔다.

- 학습 설계 시뮬레이터
- 리슨 패턴 명세 보정
- 템플릿 후보 관리
- 공식 템플릿 관리
- 보정 실행 이력

### 13.7.3 관리자 입력값

관리자는 실제 사용자가 입력할 법한 학습 조건을 직접 입력할 수 있어야 한다.

- 학습 주제
- 학습자 수준
- 학습 목표
- 학습 기간
- 선호 자료 유형
- 학습 언어
- 제외할 자료 유형
- 원하는 결과물
- 코스 깊이: 짧게 / 표준 / 심화
- 대상: 초등 / 중고등 / 성인 / 취미 / 직무 등
- 도메인
- 추가 조건

### 13.7.4 LLM 생성 결과

LLM은 다음 항목을 생성한다.

1. 추천 코스 제목
2. 코스 목표
3. 지역/리슨 구조
4. 지점별 학습 목표
5. 지점별 필요한 스킬
6. 반복 활동
7. 질문하고 해답찾기 기준
8. 자기평가 질문
9. 결과물 기준
10. 완료 조건
11. 추천 검색 명세
12. 피해야 할 콘텐츠 조건

LLM 생성 결과는 초안이며, 관리자 검토 전에는 실제 사용자 데이터에 반영하지 않는다.

### 13.7.5 리슨 패턴 명세 보정

LLM이 생성한 코스 초안은 학습 설계 패턴 기준으로 다시 보정한다. 보정 대상은 코스 구조, 지점 목표, 스킬 후보, 반복 활동, 질문하고 해답찾기 기준, 자기평가, 결과물, 완료 조건, stage_role, content_types, must_include, nice_to_have, avoid, difficulty, language를 포함한다.

### 13.7.6 보정 전후 비교 화면

관리자는 LLM 생성 원본과 패턴 보정 결과를 비교할 수 있어야 한다.

관리자는 다음 선택을 할 수 있다.

- 폐기
- 수정 후 다시 보정
- 데모 코스로 저장
- 테스트 케이스로 저장
- 템플릿 후보로 저장
- 패턴 개선 후보로 등록

### 13.7.7 저장 정책

생성된 테스트 코스는 기본적으로 실제 사용자 데이터에 반영하지 않는다. 기본값은 폐기다.

저장 옵션은 다음과 같다.

| 옵션 | 의미 |
|---|---|
| 폐기 | 테스트만 하고 저장하지 않음 |
| 데모 코스로 저장 | 데모/QA 계정용 코스로 저장 |
| 테스트 케이스로 저장 | 향후 패턴 검증용 데이터로 저장 |
| 템플릿 후보로 저장 | 관리자 검증 후 공식 템플릿으로 승격 가능 |
| 패턴 개선 후보로 등록 | 보정 결과가 좋지 않을 때 개선 항목으로 등록 |

템플릿 후보로 저장할 때는 관리자 메모를 남긴다.

### 13.7.8 템플릿의 역할

템플릿은 단순 보관용 데이터가 아니라, 실제 리슨 생성 품질을 높이기 위한 기준 데이터다.

| 구분 | 의미 |
|---|---|
| 템플릿 | 검증된 코스/리슨 설계 예시 |
| 학습 설계 패턴 | 리슨을 어떤 구조로 만들지 결정하는 규칙 |
| 리슨 명세 | 실제 생성된 리슨/지점의 목표·스킬·반복·결과물·추천검색 조건 |

공식 템플릿은 리슨 생성 시 다음 항목에 참조된다.

| 생성 항목 | 템플릿 적용 여부 |
|---|---|
| 코스/행성 구조 | 적용 |
| 지역/리슨 구성 | 적용 |
| 지점 순서 | 적용 |
| 지점 목표 | 적용 |
| 필요한 스킬 후보 | 적용 |
| 반복 활동 | 적용 |
| 결과물 기준 | 적용 |
| 완료 조건 | 적용 |
| 추천 검색 명세 | 적용 |
| must_include / avoid | 적용 |
| content_types | 적용 |
| difficulty | 적용 |

### 13.7.9 공식 템플릿 등록 기준

템플릿 후보는 바로 공식 템플릿이 되지 않는다. 관리자가 검토하고, 필요하면 여러 번 수정/보정한 뒤 공식 템플릿으로 등록한다.

공식 템플릿 등록 조건은 다음과 같다.

- 코스 목표가 명확함
- 지역/지점 구조가 과도하게 복잡하지 않음
- 지점별 목표와 스킬이 연결됨
- 반복 활동과 결과물 기준이 있음
- 추천 검색 명세가 존재함
- must_include / avoid 기준이 명확함
- 학습자 수준과 기간이 일관됨
- 관리자 검토 메모가 있음

공식 템플릿으로 등록할 때 다음 정보를 기록한다.

- 템플릿 ID
- 템플릿 이름
- 도메인
- 대상 수준
- 권장 기간
- 코스 깊이
- 생성 원본
- 보정 결과
- 승인 관리자
- 승인 일시
- 관리자 메모
- 사용 가능 여부

### 13.7.10 리슨 생성 시 템플릿 적용 흐름

공식 템플릿이 등록되면 실제 코스/리슨 생성 시 참조된다.

흐름은 다음과 같다.

사용자 학습 목표 입력 → 학습 안전 게이트 검사 → 도메인/수준/목표 유형 분석 → 관련 템플릿 검색 → 학습 설계 패턴 선택 → 템플릿을 기준 데이터로 참조 → 사용자 목표·수준·기간에 맞게 변형 → 리슨/지점 구조 생성 → 리슨 명세 생성 → 추천 검색 명세 생성

템플릿은 그대로 복사하지 않는다.

| 방식 | 판단 |
|---|---|
| 템플릿을 그대로 복사해서 코스 생성 | 지양 |
| 템플릿을 참고해 사용자 목표·수준·기간·언어·자료 선호에 맞게 변형 생성 | 권장 |

같은 기타 입문 템플릿이라도 다음처럼 다르게 생성될 수 있어야 한다.

- 초등학생 기타 입문
- 성인 취미 기타 입문
- 찬양 반주 기타 입문
- 2주 단기 기타 입문
- 3개월 심화 기타 입문

### 13.7.11 LightGBM Ranker와의 관계

관리자 학습 설계 시뮬레이터와 템플릿은 추천 품질 고도화의 전 단계다.

| 기능 | 역할 |
|---|---|
| 템플릿/리슨 패턴 명세 보정 | 좋은 후보를 찾기 위한 코스 구조와 검색 조건을 정리하는 기능 |
| LightGBM Ranker | 수집된 추천 후보를 학습 효과 기준으로 재정렬하는 기능 |

추천 품질 고도화 흐름은 다음과 같이 연결된다.

관리자 시뮬레이터 실행 → LLM 코스 생성/보정 → 템플릿 후보 저장 → 공식 템플릿 등록 → 실제 리슨 생성 시 템플릿 참조 → recommendation_search_spec 품질 개선 → 추천 후보 수집 품질 개선 → LightGBM Ranker 재정렬 품질 개선

### 13.7.12 운영 원칙

1. LLM 생성 결과는 초안이다.
2. 관리자 검토 전에는 공개하지 않는다.
3. 실제 사용자 코스에 바로 덮어쓰지 않는다.
4. 기본 저장 옵션은 폐기다.
5. 저장 시 관리자 메모를 남긴다.
6. 템플릿 후보와 공식 템플릿을 구분한다.
7. 공식 템플릿은 실제 리슨 생성 시 참조된다.
8. 템플릿은 그대로 복사하지 않고 사용자 조건에 맞게 변형 적용한다.
9. 템플릿 적용 이력은 추후 추천 품질 분석에 사용할 수 있어야 한다.

### 13.7.13 최종 기준

관리자는 임의의 학습 주제와 조건을 입력하여 LLM 기반 코스 초안과 리슨 패턴 명세 보정 결과를 미리 확인할 수 있어야 한다.

LLM은 코스 제목, 지역/지점 구조, 지점 목표, 스킬, 반복 활동, 결과물 기준, 추천 검색 명세를 생성하고, 시스템은 이를 학습 설계 패턴 기준으로 보정한다.

생성된 결과는 기본적으로 실제 사용자 데이터에 반영되지 않으며, 관리자가 선택한 경우에만 데모 코스, 테스트 케이스, 템플릿 후보, 패턴 개선 후보로 저장할 수 있다.

검증된 공식 템플릿은 실제 리슨 생성 시 학습 설계 패턴과 리슨 명세 생성에 참조된다.

## 13.8 Lumi 안내 고도화 기준

Lumi 안내 고도화는 LearnCosmos의 학습 완료율을 높이기 위한 사용자-facing 안내 레이어다. Lumi는 사용자의 학습을 대신 수행하는 튜터가 아니라, 현재 상태를 짧게 해석하고 다음 학습 행동을 부드럽게 제안하는 탐험 파트너로 유지한다.

핵심 정의는 다음과 같다.

```text
Lumi Guidance Layer
= 사용자의 행성, 지역, 지점, 탐험일지, 복습, 생활 리듬 상태를 바탕으로
  지금 필요한 다음 학습 행동을 방해 없이 안내하는 레이어
```

### 13.8.1 안내 목적

Lumi 안내는 다음 목적을 가진다.

1. 행성 생성 후 첫 지역 진입을 돕는다.
2. 학습 중단 또는 정체 상태에서 다시 이어가도록 돕는다.
3. 같은 지역을 반복해서 열지만 완료하지 못하는 상황에서 막힌 점 기록을 유도한다.
4. 탐험일지 작성, 질문하고 해답찾기, 자기평가, 결과물 정리를 유도한다.
5. 완료 후 1일, 3일, 7일, 14일 등 적절한 시점에 복습을 제안한다.
6. 사용자의 생활 리듬과 자주 학습하는 시간대를 참고해 이어가기 좋은 시간을 제안한다.
7. 학습자를 압박하지 않고 작은 행동 하나를 제안한다.

### 13.8.2 Lumi 안내 원칙

Lumi 안내는 클릭률이나 닫기율 중심으로 평가하지 않는다. Lumi 메시지는 광고형 팝업이 아니라 학습 행동을 이어가게 하는 안내이므로, 핵심 지표는 안내 후 실제 학습 행동이다.

```text
Lumi 메시지 노출
→ 사용자가 이후 어떤 학습 행동을 했는가
→ 그 행동이 학습 지속과 완료율에 도움이 되었는가
```

운영 지표는 다음을 우선한다.

| 안내 의도 | 기대 행동 |
|---|---|
| 첫 지역 진입 안내 | course_created 이후 first_lesson_opened |
| 이어하기 안내 | 마지막 학습 지역 재진입 |
| 막힘 안내 | stuck_note_written 또는 question_created |
| 기록 안내 | diary_written |
| 복습 안내 | review_started |
| 완료 안내 | lesson_completed 또는 course_completed |
| 생활 리듬 안내 | preferred_time_block 접속 후 continue_learning |

닫기율은 핵심 성과 지표가 아니라 피로도 보조 지표로만 사용한다.

### 13.8.3 안내 표면

Lumi 안내는 한 종류의 팝업으로만 제공하지 않는다. 화면 맥락에 맞게 다음 표면을 사용한다.

| 안내 표면 | 사용 위치 | 목적 |
|---|---|---|
| 상태 말풍선 | Galaxy Dashboard | 현재 행성 상태 설명 |
| Inline Nudge | Explorer Diary / 지점 화면 | 다음 행동 자연 유도 |
| Quick Action | Lumi 패널 또는 카드 | 바로 실행 가능한 행동 제공 |
| 복습 카드 | Dashboard / Diary | 복습 시점 안내 |
| 생활 리듬 안내 | Dashboard 진입 시 | 자주 학습하는 시간대 기반 이어가기 안내 |
| 모바일 Bottom Sheet | 모바일 | 짧고 명확한 안내 |

모바일에서는 복잡한 애니메이션보다 짧은 문장, 하단 카드, 명확한 CTA를 우선한다.

### 13.8.4 생활 리듬 기반 안내

LearnCosmos는 사용자의 생활 패턴을 감시하는 방식이 아니라, 학습 리듬을 돕는 방식으로 안내한다. 사용자-facing 명칭은 `루미 학습 리듬 안내` 또는 `나에게 맞는 탐험 시간 추천`으로 사용한다.

사용할 수 있는 신호는 다음과 같다.

```text
- 자주 학습하는 요일
- 자주 학습하는 시간대
- 평균 학습 세션 길이
- 마지막 학습일
- 보통 며칠 간격으로 돌아오는지
- 복습 안내 후 실제 재방문 여부
- 같은 지역 반복 열람 여부
```

예시 메시지는 다음과 같다.

```text
보통 이 시간에 탐험을 잘 이어가셨어요.
오늘은 15분만 마지막 지역을 이어가볼까요?
```

```text
이 지역을 탐험한 지 3일이 지났어요.
지난 질문 하나만 다시 확인해볼까요?
```

### 13.8.5 금지 기준

Lumi 안내에서는 다음을 금지한다.

1. 학습자를 평가하거나 비난하는 표현을 사용하지 않는다.
2. “공부하지 않았다”, “게으르다” 같은 압박형 문구를 사용하지 않는다.
3. 사용자의 생활 패턴을 감시하는 느낌을 주지 않는다.
4. 팝업을 과도하게 반복 노출하지 않는다.
5. Lumi가 학습자의 선택을 대신 결정하지 않는다.
6. Lumi 메시지를 자동으로 운영 반영하거나 사용자에게 강제하지 않는다.

좋은 표현은 다음 방향을 따른다.

```text
잠시 쉬어도 괜찮아요.
다시 이어가기 좋게 마지막 지역을 열어둘게요.
오늘은 10분 복습만 해도 충분해요.
```

### 13.8.6 데이터 기준

Lumi 안내 데이터는 원문보다 행동 이벤트 중심으로 저장한다.

```text
learning_events
- course_created
- first_lesson_opened
- lesson_opened
- lesson_reopened
- resource_selected
- diary_written
- stuck_note_written
- question_created
- review_started
- lesson_completed
- course_completed
- return_after_days
```

```text
lumi_guidance_events
- user_id
- course_id
- lesson_id
- guidance_intent
- trigger_type
- message_variant
- surface_type
- expected_outcome_event
- outcome_window_minutes
- shown_at
- next_event_type
- next_event_at
- outcome_matched
```

핵심은 clicked / dismissed가 아니라 expected_outcome_event와 outcome_matched다.

## 13.9 Hermes Agent 운영 분석 기준

Hermes Agent는 LearnCosmos의 사용자-facing 에이전트가 아니다. Hermes Agent는 LearnCosmos의 운영 패턴 데이터를 분석해 학습 완료율을 높이는 기획을 보조하는 내부 분석 에이전트로 사용한다.

핵심 정의는 다음과 같다.

```text
Hermes Agent
= LearnCosmos의 코스 생성 결과, Lumi 안내 이벤트, 학습 운영 데이터를 분석하여
  학습 완료율을 높이기 위한 기획안, 개선 가설, Codex 작업 지시문 초안을 제안하는 내부 분석 에이전트
```

### 13.9.1 역할 분리

| 구성 | 역할 |
|---|---|
| LearnCosmos Core | 실제 학습 서비스, 데이터 저장, 사용자 경험 제공 |
| Lumi Engine | 학습자 화면에서 다음 행동 안내 |
| Completion Metrics | 학습 완료율 분석 지표 생성 |
| Hermes Agent | 운영 데이터 분석, 개선 가설, 기획안 제안 |
| Codex | 검토된 개선안 구현 |
| 운영자 | Hermes 제안 검토, 우선순위 결정, 반영 승인 |

Hermes는 사용자를 직접 안내하지 않는다. Hermes는 Lumi Engine을 자동으로 교체하지 않고, production DB를 직접 수정하지 않는다.

### 13.9.2 분석 질문

Hermes Agent가 다루는 핵심 질문은 다음과 같다.

```text
1. 학습자는 어느 단계에서 가장 많이 멈추는가?
2. 행성 생성 후 첫 지역 진입률은 어떤가?
3. 탐험일지를 작성한 사용자는 완료율이 더 높은가?
4. 추천 자료 선택 후 실제 학습으로 이어지는가?
5. 같은 지역을 반복해서 여는 사용자는 어떤 안내가 필요한가?
6. 복습 안내는 몇 일 간격이 재방문에 도움이 되는가?
7. Lumi 안내가 실제 완료율에 도움이 되는 구간은 어디인가?
8. 완료율이 높은 코스 생성 구조는 무엇인가?
9. 완료율이 낮은 코스 생성 구조는 무엇인가?
10. 다음 실험해야 할 UX 개선안은 무엇인가?
```

분석 기준은 클릭률이 아니라 학습 퍼널이다.

```text
행성 생성
→ 첫 지역 진입
→ 탐험목표 선택
→ 학습 진행
→ 탐험일지 작성
→ 지역 완료
→ 복습
→ 행성 완료
```

### 13.9.3 Hermes에게 넘길 데이터

Hermes에는 원문 데이터가 아니라 비식별·집계 데이터를 넘긴다.

넘겨도 좋은 데이터는 다음과 같다.

```text
- 행성 생성 수
- 첫 지역 진입률
- 지역 완료율
- 탐험일지 작성률
- 복습 시작률
- 추천 자료 선택률
- Lumi 안내 의도별 outcome_matched 비율
- 시간대별 학습 지속률
- 사용자 그룹별 완료 퍼널
- 코스 생성 평가 점수와 실제 완료 결과 비교 데이터
```

넘기면 안 되는 데이터는 다음과 같다.

```text
- 사용자 실명, 연락처
- 사용자 API Key
- 결제 정보
- 탐험일지 원문 전체
- 비공개 질문 원문
- 비공개 결과물 본문
- production DB 직접 접근 권한
```

### 13.9.4 Hermes 산출물

Hermes는 다음 형식의 분석 산출물을 만든다.

```text
LearnCosmos Completion Intelligence Report

1. 전체 완료율 요약
2. 주요 이탈 구간
3. 완료율이 높은 사용자 흐름
4. 완료율이 낮은 사용자 흐름
5. 코스 생성 단계 개선 후보
6. Lumi 안내 개선 후보
7. Explorer Diary 개선 후보
8. 추천 엔진 개선 후보
9. 복습 간격 개선 후보
10. 다음 A/B 테스트 제안
11. Codex 작업 지시문 초안
```

Hermes의 산출물은 운영자가 검토한 뒤에만 Codex 작업으로 연결한다.

### 13.9.5 버전업 대응 원칙

Hermes Agent는 빠르게 버전업될 수 있으므로 LearnCosmos 핵심 런타임에 직접 결합하지 않는다. Hermes는 분석 보조 도구로 분리하고, 결과는 항상 검토 후 반영한다.

운영 원칙은 다음과 같다.

```text
1. Hermes는 production DB에 직접 접근하지 않는다.
2. Hermes는 사용자에게 직접 메시지를 보내지 않는다.
3. Hermes는 Lumi Engine을 자동 수정하지 않는다.
4. Hermes에는 비식별·집계 데이터만 넘긴다.
5. Hermes 결과는 운영자 검토 후 Codex 작업으로 반영한다.
6. Hermes 버전은 운영 환경에서 고정하고, 새 버전은 staging에서 검증한다.
7. Hermes가 바뀌어도 LearnCosmos의 이벤트 구조와 완료율 지표는 자체 자산으로 유지한다.
```

## 13.10 코스 생성 단계 완료율 검토 기준

LearnCosmos의 학습 완료율 개선은 운영 데이터 분석에서만 시작하지 않는다. 코스가 생성되는 순간부터 이 코스가 완료 가능한 구조인지 검토해야 한다.

핵심 정의는 다음과 같다.

```text
Course Completion Readiness
= 생성된 행성탐험계획이 실제 학습자가 시작하고, 기록하고, 완료하기 쉬운 구조인지 평가하는 기준
```

Hermes Agent는 생성된 코스 구조와 실제 운영 데이터를 함께 분석하여, 완료율 높은 코스 생성 규칙을 개선하는 기획 보조 역할을 한다.

### 13.10.1 검토 질문

코스 생성 단계에서 다음 질문을 검토한다.

```text
1. 이 행성은 첫 지역을 시작하기 쉬운가?
2. 학습 목표가 너무 추상적이지 않은가?
3. 지역 수가 많아서 시작 전부터 부담스럽지 않은가?
4. 각 지역이 하나의 행동 단위로 쪼개져 있는가?
5. 각 지역마다 탐험일지에 쓸 만한 관찰점이 있는가?
6. 추천 자료가 붙지 않으면 막히는 지역은 없는가?
7. 학습자가 중간에 성취감을 느낄 지점이 있는가?
8. 완료 조건이 분명한가?
9. 결과물 또는 자기 언어화 단계가 있는가?
10. 비슷한 구조의 과거 코스는 완료율이 어땠는가?
```

### 13.10.2 Course Completion Readiness 평가 항목

| 항목 | 의미 |
|---|---|
| 목표 명확도 | 사용자가 무엇을 할 수 있게 되는지 분명한가 |
| 범위 적정성 | 너무 넓거나 장기 프로젝트처럼 과하지 않은가 |
| 첫 행동 가능성 | 첫 지역을 바로 열고 시작할 수 있는가 |
| 지역 단위 적정성 | Lesson이 너무 크거나 작지 않은가 |
| 난이도 흐름 | 쉬운 것에서 어려운 것으로 이어지는가 |
| 기록 가능성 | 탐험일지에 남길 질문, 막힘, 결과물이 있는가 |
| 결과물 연결성 | 마지막에 남길 작은 결과물이 있는가 |
| 추천 자료 연결성 | 각 지역에 탐험목표를 붙이기 쉬운가 |
| 모바일 부담도 | 모바일에서 부담 없이 진행 가능한가 |
| 완료 예측 | 실제 완료될 가능성이 높은가 |

기존 AI 평가 항목이 있다면 goal_achievability, flow_quality, content_fitness, difficulty_balance를 유지하되, 완료율 관점의 평가 항목을 추가한다.

### 13.10.3 생성 직후 UX 기준

코스가 잘 생성되어도 생성 직후 사용자가 무엇을 해야 할지 모르면 이탈한다. 따라서 생성 직후 Lumi 안내와 첫 행동 CTA를 제공한다.

예시 메시지는 다음과 같다.

```text
행성이 만들어졌어요.
오늘은 전체를 다 보지 말고, 첫 지역 하나만 가볍게 열어볼까요?
[첫 지역 열기]
```

측정 지표는 다음과 같다.

| 지표 | 의미 |
|---|---|
| course_created_to_first_lesson_opened | 생성 후 첫 지역 진입률 |
| course_created_to_resource_selected | 생성 후 첫 탐험목표 선택률 |
| course_created_to_diary_written | 생성 후 첫 탐험일지 작성률 |
| time_to_first_lesson_opened | 첫 지역 진입까지 걸린 시간 |
| draft_abandon_rate | 생성 후 방치율 |

### 13.10.4 Hermes 분석 루프

코스 생성 품질과 실제 완료율은 다음 루프로 비교한다.

```text
1. 사용자가 행성 생성
2. LearnCosmos가 코스 초안 저장
3. Course Completion Readiness 평가
4. 사용자가 실제 학습 진행
5. 운영 데이터 수집
6. Hermes가 생성 품질과 실제 완료율 비교
7. 완료율 높은 코스 패턴 도출
8. 코스 생성 프롬프트 / 평가 기준 / Lumi 안내 / Explorer Diary UX 개선
```

핵심 비교 질문은 다음이다.

```text
생성 당시에는 좋아 보였던 코스가 실제로 완료됐는가?
완료율이 높은 코스는 생성 구조가 어떻게 달랐는가?
완료율이 낮은 코스는 어느 설계 요소에서 문제가 있었는가?
```

### 13.10.5 개선 대상

Hermes 분석 결과는 다음 영역 개선에 사용한다.

| 개선 영역 | 개선 예시 |
|---|---|
| 입력 단계 | 너무 넓은 목표일 때 구체화 질문 추가 |
| 생성 프롬프트 | 첫 지역은 10\~15분 안에 시작 가능하게 생성 |
| 지역 구조 | Lesson을 지식 단위가 아니라 행동 단위로 분해 |
| 탐험일지 연결 | 지역마다 한 줄 기록, 막힌 점, 질문, 결과물 기준 제공 |
| 생성 직후 Lumi 안내 | 첫 지역 열기, 짧은 시작 행동 제안 |
| 평가 기준 | Course Completion Readiness 점수화 |

## 16. 최종 요약

LearnCosmos는 LearnWeaver의 자산을 기반으로 다시 시작하되, 사용자에게 보이는 기준은 LearnCosmos로 통일한다.

핵심은 코스 생성이 아니라 학습 경험화다.

LearnCosmos의 제품 중심은 다음 세 가지다.

1. Galaxy Dashboard에서 학습 세계를 조망한다.
2. Explorer Diary에서 학습을 기록하고 소화한다.
3. Lumi가 다음 행동을 친절하게 안내한다.

이 세 가지가 LearnCosmos의 1차 제품 기준이다.
